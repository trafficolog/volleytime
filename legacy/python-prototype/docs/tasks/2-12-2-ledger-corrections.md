# Task 2.12.2: Создание корректирующих записей

## Цель

Кнопка «↩️ Создать корректировку» в карточке кассовой записи: позволяет создать новую запись, которая компенсирует ошибку в исходной (сторно-операция). Физическое удаление запрещено.

## Контекст

Бухгалтерский подход: ошибочные записи остаются, к ним добавляются корректирующие. Это сохраняет audit trail и баланс прошлого периода.

Пример:
- Исходная запись: income 20 BYN, описание «оплата Пети» (ошибка — должно быть 15)
- Корректирующая запись: income -5 BYN, описание «correction of #N: ошибка в сумме»
- В итоге баланс правильный, история всех правок сохранена

## Что должно быть сделано

- Доработка модели `LedgerEntry`:
  - Новое поле `corrects_entry_id: Mapped[Optional[int]] = mapped_column(ForeignKey("ledger_entries.id"), nullable=True)`
  - Self-relationship `corrected_by: Mapped[Optional["LedgerEntry"]] = relationship(...)`
- Кнопка «↩️ Создать корректировку» (Task 2.12.1) → FSM `CreateCorrection`:
  1. `waiting_amount` — Decimal со знаком (положительный = добавить, отрицательный = убрать)
  2. `waiting_description` — текст
- Логика:
  - Тип новой записи = тип исходной (income → income, expense → expense)
  - Категория = категория исходной
  - `corrects_entry_id = original.id`
  - В описании автоматически префикс «correction of #<original_id>:»
- В карточке исходной записи (Task 2.12.1) — если есть `corrected_by`, показать «↩️ Скорректировано записью #M»
- AdminLog (action="ledger_correction_created", details={original_id, new_id, amount})

## Критерии приёмки

- Поле `corrects_entry_id` добавлено в модель
- FSM создаёт новую запись с правильным типом и связью
- В карточке корректировки видна ссылка на исходную, и наоборот
- Баланс пересчитывается корректно с учётом корректировок
- Тест: `LedgerService.get_balance()` суммирует все записи, включая корректировки

## Подсказки

- Сумма корректировки может быть отрицательной — нужно поддержать в форме ввода (`Decimal('-5.00')`).
- Балансовый расчёт: `income_total = sum(amount for type=income)` уже работает, потому что отрицательная корректировка income уменьшит общий income — это правильно.

## Не делать

- Не давать создавать корректировку к корректировке (запретить через проверку `not original.corrects_entry_id`).
- Не делать физическое удаление — даже после корректировки исходная запись остаётся.
- Не менять `created_at` корректирующей записи — у неё своё время создания.

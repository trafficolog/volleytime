# Task 2.13.3: Создание, редактирование, деактивация плана

## Цель

Полный CRUD планов через UI: создание нового, редактирование полей существующего, деактивация (а не удаление).

## Контекст

Поверх Task 2.13.2 — кнопки и FSM.

## Что должно быть сделано

### Создание

- Кнопка «➕ Создать план» в списке (Task 2.13.2) → FSM `CreatePlan`:
  1. `waiting_code` — короткий код, уникальный (валидация: `^[a-z0-9]{2,16}$`)
  2. `waiting_title` — название (например, «Месячный»)
  3. `waiting_sessions` — int 1-100
  4. `waiting_price` — Decimal
  5. `waiting_valid_days` — int 1-365
  6. Подтверждение
- Применение: создание SubscriptionPlan в БД с `is_active=true`, `sort_order=max+1`
- AdminLog

### Редактирование

- Кнопки в карточке плана: «✏️ Цена», «✏️ Сессий», «✏️ Срок», «✏️ Название»
- FSM `EditPlanField.waiting_value` для каждого поля
- При изменении цены/сессий/срока — предупреждение: «Уже купленные {N} абонементов не пересчитываются»
- AdminLog с old/new

### Деактивация / Активация

- Кнопка «🚫 Деактивировать» (если is_active) или «🔁 Активировать»
- Деактивация:
  - Установить `is_active = false`
  - План больше не показывается в публичном меню покупки
  - Уже купленные подписки продолжают работать
- Активация: обратно
- AdminLog

### Защита

- Нельзя удалить (физически) — только деактивировать.
- Изменения `code` — запрещено (уникальный идентификатор).
- Уменьшение `valid_days` — окей, не влияет на купленные.

## Критерии приёмки

- Создание плана с уникальным кодом работает
- Дубль кода → отказ
- Редактирование любого поля работает (кроме code)
- Деактивированный план не показывается в покупке (см. handlers/player/subscriptions.py)
- Активные подписки на деактивированный план продолжают работать
- AdminLog ведётся

## Подсказки

- Валидация code: `re.match(r"^[a-z0-9]{2,16}$", code)`.
- При создании — `sort_order = (await session.scalar(select(func.max(SubscriptionPlan.sort_order))) or 0) + 1`.

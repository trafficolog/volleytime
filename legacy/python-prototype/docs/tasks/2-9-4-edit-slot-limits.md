# Task 2.9.4: Изменение лимитов слотов для существующей тренировки

## Цель

В экране редактирования тренировки (Task 2.9.1) изменение `max_main_slots` и `max_rotation_slots` — особый случай: возможно ре-распределение существующих бронирований.

## Контекст

Сценарии:
- «Тренер сказал, что зал большой, можно 16 человек вместо 14» → увеличить main с 12 до 14 → из waitlist могут продвинуться двое.
- «Поломалась половина зала, играем 6 на 6» → уменьшить main с 12 до 10 → последние двое из main «улетают» в rotation или waitlist.

Это **деликатная** операция: затрагивает чужие места. Нужно явное подтверждение.

## Что должно быть сделано

- При смене `max_main_slots`:
  - Если новый ≥ текущего занятого — просто обновить лимит, попытаться promote_from_waitlist пока есть свободные слоты
  - Если новый < текущего занятого — показать сообщение: «Сейчас занято K main-слотов. После изменения K - new_limit игроков переместятся из main в rotation/waitlist. Продолжить? [Да] [Отмена]»
- Если подтверждено:
  - Найти последних K - new_limit подтверждённых main-бронирований (`ORDER BY created_at DESC LIMIT K-new`)
  - Попытаться переместить в rotation, если там есть место
  - Не попавшие — в waitlist
  - Уведомить каждого о смене slot_type
  - AdminLog
- Аналогично для rotation
- При увеличении лимита — продвижение из waitlist по FIFO

## Критерии приёмки

- Уменьшение лимита main с 12 до 10 при 12 занятых: 2 последних переходят в rotation или waitlist
- Увеличение лимита main с 12 до 14 при 14 занятых main + 2 waitlist: 2 из waitlist становятся main
- Уведомления приходят затронутым игрокам
- Корректное состояние счётчиков после операции

## Подсказки

- Существующий `BookingService.promote_from_waitlist` пригодится для увеличения.
- Для уменьшения — новая функция `BookingService.demote_excess_bookings(training_id, slot_type, new_limit)`.

## Не делать

- Не менять лимиты для отменённых/прошедших тренировок.
- Не уменьшать лимит ниже 0.
- Не двигать `confirmed` со статуса в `pending_confirmation` — просто меняем `slot_type`.

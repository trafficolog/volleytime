# Phase 2.5: Расширенная админ-панель

**Цель.** Дать админу полный контроль над сущностями системы через бот: игроки, тренировки, записи, абонементы, касса, планы, настройки. Без редактирования кода и БД.

## Контекст

После Phase 2 бот может работать в реальной группе, но в режиме «всё или ничего»: тренировка создана с фиксированными параметрами, изменить нельзя; запись игрока — только им самим; абонементы — только покупка по фиксированным планам; настройки — в коде.

Реальная жизнь требует больше гибкости: «перенесите тренировку на час», «запишите Петю, он без телефона», «продлите абонемент на неделю», «давайте поднимем цены». Без этих возможностей бот будет источником трения, а не пользы.

**Логическое место фазы:** между Phase 2 (manual payments) и Phase 3 (bePaid).

**Не блокирует:** Phase 4 (scheduler) можно делать параллельно. Phase 3 — после регистрации ИП/НПД.

## Definition of Done

- Админ может видеть список всех игроков, открыть карточку любого, посмотреть его историю.
- Админ может отредактировать любое поле существующей тренировки (кроме истории).
- Админ может создать серию повторяющихся тренировок одним действием.
- Админ может записать игрока на тренировку «за него», снять чужую запись, переместить из waitlist.
- Админ может создать абонемент игроку вручную (подарок), продлить срок, изменить остаток.
- Админ может отредактировать или удалить запись в кассе.
- Админ может управлять планами абонементов через UI (создать, изменить цену/срок, деактивировать).
- Базовые настройки бота (базовая цена, окно записи, лимиты слотов) меняются через админ-меню.

## Технические заметки

### AdminLog везде

Любое действие админа над чужими сущностями (правка чужой брони, изменение цены, корректировка кассы) должно писаться в `AdminLog` (модель уже есть с Phase 1). Это:
- audit trail на случай вопросов («кто изменил?»)
- защита от случаев «не я» (видно в логе)
- материал для статистики в Phase 5

Хелпер `AdminLogService.record(admin_id, action, entity_type, entity_id, details: dict)` — добавить и использовать везде.

### FSM для редактирования

Для редактирования полей — паттерн «карточка → кнопка с полем → FSM с одним шагом → возврат к карточке».

```
[Карточка игрока Петя]
├ Имя: Пётр Петров        [✏️ Изменить]
├ Phone: +375291234567    [✏️ Изменить]
├ Статус: активен         [🚫 Заблокировать]
└ Роль: player            [👑 Сделать админом]
```

### Уведомления

Если правка касается чужого игрока (например, ему создан абонемент в подарок) — уведомить его. Если правка административная (изменение цены тренировки) — не спамить.

### Подтверждение деструктивных действий

Любое действие, которое нельзя откатить (удаление записи в кассе, блокировка игрока, отмена брони чужого) — двухшаговое подтверждение через inline-клавиатуру.

### Settings через БД

В Phase 2.5 простые настройки выносятся из `src/config.py` в новую таблицу `app_settings`. Конфиг файлов остаётся для секретов (BOT_TOKEN, BEPAID_SECRET_KEY) — их менять через UI нельзя по соображениям безопасности.

Settings, которые ДА переносим в БД:
- `base_training_price` (15 BYN)
- `booking_closes_hours_before` (2)
- `default_max_main_slots` (12)
- `default_max_rotation_slots` (2)
- `pending_payment_ttl_minutes` (15)
- `cancellation_refund_hours_before` (24)
- `waitlist_promotion_ttl_minutes` (30)
- `reminder_24h_enabled`, `reminder_2h_enabled` (bool)

Settings, которые НЕТ:
- `BOT_TOKEN`, `BEPAID_*` (секреты)
- `DATABASE_URL`, `PUBLIC_URL` (инфраструктура)
- `ADMIN_TELEGRAM_IDS` (см. ниже)

### Управление админами

В Phase 1 админ определяется через `ADMIN_TELEGRAM_IDS` в `.env`. В Phase 2.5 это становится двухуровневым:
- **Root admin** — те, кто в `.env`. Их роль нельзя снять через бот. Они могут управлять остальными админами.
- **Promoted admin** — назначенные через бот (`User.role = admin`). Root может разжаловать.

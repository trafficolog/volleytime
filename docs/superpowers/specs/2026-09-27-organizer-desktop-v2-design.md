# Task 5.15.1 — desktop-кабинет организатора v2

Дата: 2026-09-27. Основание: [SDD-карточка](../../tasks/5-15-1-organizer-desktop-v2.md), [карта v2](../../design/2026-09-23-reference-v2.md), `4 Кабинет организатора.html`, `screens-web.jsx`, `screens-web-forms.jsx` и решения пользователя по R0.6. Референс задаёт композицию, токены и состояния, но не права, данные или новые функции.

## Цель и граница

Открыть организатору полноценный браузерный кабинет без Telegram по `/app/orgs/:orgId`, сохранив `/m` как Telegram-first Mini App. Оба клиента используют существующие сессию, tenant-проверку, API, модель прав и бизнес-правила. Узкий браузерный viewport остаётся в `/app`, а не перенаправляется в Telegram. В 5.15.1 входят shell, обзор, события, игроки, абонементные планы и настройки. Денежные операции и отдельные экраны «Оплаты»/«Касса» принадлежат 6.10.1; сквозная визуальная, функциональная и Telegram-host QA — 8.10.3.

## Маршруты и доступ

| Web-маршрут                                                                                                | Назначение и источник                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/app`                                                                                                     | Выбор доступной управляемой организации; при одной подходящей группе — переход на её обзор. Пустое состояние ведёт к созданию организации через существующий API. |
| `/app/orgs/new`                                                                                            | Создание организации через `POST /api/organizations`; после ответа — обзор созданной группы.                                                                      |
| `/app/orgs/:orgId`                                                                                         | Обзор на основе `GET /api/organizations/:orgId/dashboard` и данных организации.                                                                                   |
| `/app/orgs/:orgId/events`                                                                                  | Предстоящие/прошедшие события из существующего списка; список и календарь — два представления одних данных, без второго источника истины.                         |
| `/app/orgs/:orgId/events/new`, `/app/orgs/:orgId/events/:eventId`, `/app/orgs/:orgId/events/:eventId/edit` | Создание, деталь/состав и редактирование события через существующие API и правила.                                                                                |
| `/app/orgs/:orgId/members`                                                                                 | Состав, заявки и доступные действия модерации из действующего API.                                                                                                |
| `/app/orgs/:orgId/invite`                                                                                  | Приглашения в группу через существующие `invites` endpoints и политики ролей; без Telegram-специфичного оформления.                                               |
| `/app/orgs/:orgId/plans`                                                                                   | Планы абонементов и действующие операции с ними, если настройка группы включена.                                                                                  |
| `/app/orgs/:orgId/settings`                                                                                | Настройки группы; редактирование, переключатель абонементов и архивирование доступны только владельцу.                                                            |

Web-shell допускает только активных `owner`/`organizer` из ответа `GET /api/organizations/:orgId`. Игрок, ассистент, ожидающий, заблокированный и посторонний не видят административный shell или данные: отдельное понятное состояние доступа без показа защищённого содержимого. Серверные запреты остаются решающими; скрытие кнопок не заменяет авторизацию. Неавторизованный пользователь идёт в существующий `/auth/login` с безопасным возвратом к web-маршруту. Переключатель групп берёт только доступные управляемые группы из `GET /api/organizations` и при смене `orgId` сбрасывает локальные формы, запросы и состояния предыдущей группы. Архивная/приостановленная группа следует существующей политике доступа и получает отдельное состояние, а не фиктивный пустой dashboard.

## Shell и визуальный язык

При ширине desktop сохраняются боковая навигация, название/переключатель группы, верхняя панель и рабочая область с сеткой карточек по очищенному референсу. Используются уже внедрённые токены Bento Bold: Oswald для заголовков/чисел, Golos Text для интерфейса, холодная белая/серая поверхность, брендовый синий и оранжевый акцент. Не копируются старые стили, макетные цифры, кредиты, неработающие поиск/уведомления, тарифы и ссылки на будущие сборы/отчёты.

Основная навигация: «Обзор», «События», «Игроки», «Абонементы» при `subscriptionsEnabled=true`, «Настройки». Пункты «Оплаты» и «Касса» добавляет 6.10.1 после реализации реальных экранов. Выключение абонементов скрывает пункт из основной навигации, но не удаляет планы/покупки; защищённая прямая ссылка может показать сохранённые данные без CTA создания/продажи до включения. Состояние навигации определяется ответом API, не localStorage. Логотип ведёт к выбору группы или текущему обзору; видимые переходы — настоящие ссылки с корректным URL и поддержкой back/forward.

На узком viewport sidebar превращается в доступную раскрываемую навигацию, карточки/таблицы перестраиваются без горизонтальной прокрутки страницы, а действия остаются достижимыми. На 200% zoom при обычном desktop-окне контент и диалоги не обрезаются; горизонтальная прокрутка допускается только внутри действительно табличного участка с доступными заголовками. Не вводится другой мобильный набор бизнес-экранов.

## Экраны и реальные данные

**Обзор.** Композиция референса — заметная финансовая карточка и соседние блоки ожидающих оплат/ближайшего события — заполняется только реальными `manager.balance`, `manager.pendingCount`, `manager.pendingAmount` и `upcoming` из `/dashboard`. Если данных нет, показывается предметное пустое состояние. Ссылки на денежные разделы появляются только вместе с 6.10.1; в этой задаче нет подтверждения оплат в overview. Макетные графики, тренды, приросты и общее количество игроков без подтверждённого источника не показываются.

**События.** Список использует существующие фильтры API `upcoming`/`past`; календарь группирует полученные события по дате в часовом поясе группы и не создаёт отдельную доменную модель. Если серверная выборка ограничена или постранична, календарь не выдаёт неполный месяц за полный: отображает только загруженный период с явной навигацией/подгрузкой по поддерживаемому контракту; при невозможности корректной полноты календарное представление ограничивается загруженными событиями и явно это обозначает. Деталь показывает серверный статус, вместимость, состав и очередь; публикация, отмена события, снятие записи и отметка посещения используют действующие endpoints. Формы создания/редактирования содержат только рабочие поля текущего `EventForm`: дата/время и длительность в timezone группы, площадка, вместимость, фиксированная цена, дедлайн отмены, описание и публикация. Нет split, credits, повторений и макетных шаблонов. После успешной мутации экран перечитывает серверное состояние; ошибка оставляет исходные данные и показывает причину.

**Игроки.** Активные, заявки и заблокированные — статусы `GET /members`; подтверждение, отклонение, блокировка и разблокировка идут по существующим операциям и ограничениям `canModerate`. Приглашение ведёт в рабочий поток группы через существующий API, не в старый бот и не в макетный QR события. Смена ролей показывается только владельцу и только в пределах серверной политики. Нет fake bulk-действий или экспорта.

**Абонементы.** Список, создание, редактирование и архивирование планов используют существующие `plans` endpoints и права owner/organizer. Значения денег конвертируются теми же shared-утилитами и отображаются с серверной валютой/единицами. При выключенной настройке запрещены новые планы и покупки по правилу 5.13.21; сохранённые планы доступны для просмотра по прямой ссылке, без обхода запрета. Статистика активных покупок и ручные напоминания из JSX не воспроизводятся, если нет действующего API.

**Настройки.** Имя, город, описание, режим принятия участников и `subscriptionsEnabled` читаются из `GET /api/organizations/:orgId`; сохранение — через текущий owner-only `PATCH`. Используется `organizationSettingsPayload`, чтобы отсутствие поля не меняло переключатель случайно. После PATCH значение перечитывается и подтверждается сервером; ошибка не оставляет ложное «сохранено». Архивирование — отдельная явная подтверждаемая операция owner-only. Организатор может видеть объяснение прав, но не редактируемую форму. Действующий аудит может быть доступен отдельной ссылкой только при подтверждённом API/праве; фиктивного журнала нет.

## Состояния, безопасность взаимодействия и доступность

Для каждой загрузки: skeleton/ожидание, пустое состояние, ошибка с повтором, 401 с маршрутом входа, 403/404 без утечки данных, suspended/archived по действующему статусу. Прямые ссылки и обновление страницы должны работать. Асинхронный ответ старого `orgId` или старого маршрута не должен перезаписать новый экран либо отправить мутацию в покинутую группу; кнопки мутаций блокируются только на время собственного запроса, повторные нажатия не создают дубликатов. Подтверждения разрушительных действий — web-диалоги, не Telegram SDK/haptics.

Sidebar — семантическая навигация, текущий пункт имеет `aria-current`; страницы имеют один `h1`, skip-link к основному содержимому, видимый keyboard focus. Меню группы/узкого viewport, табы и диалоги доступны с клавиатуры; управление фокусом и Escape проверяются. Поля подписаны, ошибки связаны с полями и объявляются, статус после сохранения озвучивается. Цвет не единственный носитель статуса. Соблюдаются reduced-motion и масштаб 200%; динамические числовые карточки не должны ломать раскладку.

## Проверка и порядок

1. По SDD-карточке: зафиксировать тестами красные сценарии доступа и маршрутов, смены группы, каждого действия/ошибки, отключённых абонементов и отличия от Mini App; затем red → green → refactor небольшими шагами.
2. Компонентные/API тесты подтверждают один и тот же статус, цену, валюту и право на обеих поверхностях. Не дублировать доменные правила в desktop-коде.
3. Браузерный smoke: 1280/1440 px, узкий viewport, 200% zoom; список/календарь/деталь/форма, состав, планы, owner и organizer, игрок без админ-доступа, пустые/ошибочные состояния, клавиатура и back/forward. Скриншоты сравниваются с актуальным `4 Кабинет организатора.html`, но только для MVP-элементов.
4. Обязательные gates: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test` с PostgreSQL, `pnpm build`; review и отдельный PR задачи в `main`. Затем 6.10.1, 8.10.3 и общая приёмка R0.6. Ни эта задача, ни зелёные repo-тесты сами по себе не разрешают продвижение `prod` или не доказывают Telegram QA.

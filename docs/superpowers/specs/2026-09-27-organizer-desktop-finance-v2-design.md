# Task 6.10.1 — desktop-оплаты и касса v2

Дата: 2026-09-27. Основание: [SDD-карточка](../../tasks/6-10-1-organizer-desktop-finance-v2.md), [план R0.6](../../RELEASES.md), `screens-web.jsx`, `screens-web-forms.jsx` и решения пользователя по MVP. Референсы задают композицию и визуальный язык, но не добавляют финансовые функции, которых нет в домене.

## Цель и граница

Дать владельцу и организатору отдельные desktop-разделы «Оплаты» и «Касса» в кабинете `/app/orgs/:orgId`. Ожидающие платежи обрабатываются по одному через действующие серверные переходы. История платежей должна быть полной и постраничной: `pending`, `succeeded`, `cancelled`, `refunded`, включая отклонённые платежи. Касса показывает действительный баланс, поступления, расходы и журнал; ручные операции используют существующий append-only ledger. Мини-приложение и его API ожидания платежей продолжают работать без изменения контракта.

Эта задача не является релизом R0.6 целиком. Она следует за готовым desktop-shell 5.15.1 и предшествует сквозной QA 8.10.3. В `prod` она не продвигается отдельно.

## Архитектура и контракты

В `desktopNavItems` добавляются отдельные ссылки `/app/orgs/:orgId/payments` («Оплаты») и `/app/orgs/:orgId/cashbox` («Касса») для доступного owner/organizer shell. Каждая страница сохраняет свой URL, состояние загрузки и повтор запроса; при смене `orgId` данные, фильтры, открытая форма и незавершённые ответы прежней группы не должны появиться в новой.

Существующие `GET /api/organizations/:orgId/payments` (только ожидающие), `POST /payments/:paymentId/confirm|reject` и `GET|POST /ledger` сохраняют поведение. Для истории добавляется отдельный `GET /api/organizations/:orgId/payments/history`. Он использует действующую проверку организации и `requireCanManageContent`, затем `paymentService.listHistory`; чужая организация и роль без права управления не получают платёжные данные. Ответ содержит `payments` и `nextCursor`, без сырой записи БД и закрытых полей пользователя.

`history` принимает необязательные `status` из четырёх существующих статусов, `limit` (по умолчанию 50, максимум 100) и непрозрачный `cursor`. Неверный статус, лимит или курсор дают 400, а не молчаливый произвольный запрос. Сортировка — `createdAt DESC, id DESC`; keyset-курсор хранит пару даты/ID и исключает повтор/пропуск при равных датах. `nextCursor=null` означает конец выборки. При смене фильтра или успешной мутации клиент сбрасывает курсор и перечитывает первую страницу; фильтрованная выдача не обещает snapshot при одновременных изменениях статуса.

Строка истории содержит ID, статус, сумму в minor units, валюту, способ, дату создания, доступные `confirmedAt`/`refundedAt`, публичное имя/username игрока и доступный контекст события или плана. Если бронь/план уже удалены, платеж остаётся в истории с нейтральным обозначением недоступного объекта. `cancelled` показывается как «Отменён»: текущая схема не хранит отдельную причину или дату отмены, поэтому нельзя утверждать, что каждую такую запись отклонил организатор. Новое поле причины или миграция для реконструкции старых отмен в 6.10.1 не вводится.

## Экраны и поток данных

**Оплаты.** Первый блок — все ожидающие из действующего endpoint с игроком, назначением, суммой/валютой, способом и датой. Кнопки подтверждения и отклонения работают по одному платежу; отклонение предваряется web-подтверждением с последствием для записи/абонемента. На время операции блокируется её строка, без массового действия. После успеха заново загружаются ожидание и первая страница истории. При конфликте `payment.not_pending` или параллельном действии показывается понятное сообщение и данные перечитываются; клиент не выдумывает новый статус. Ни один итог не складывает разные валюты.

Ниже — полная история со статусным фильтром и «Показать ещё». Доступны все четыре статуса, включая ещё ожидающие, чтобы слово «полная» не означало скрытую часть записей. Статус дан текстом и цветом; дата отмены не показывается, поскольку её нет. История только для просмотра: повторных подтверждений, возвратов и иных новых денежных действий из неё нет.

**Касса.** Отдельная страница сохраняет композицию референса: заметный баланс и карточки доходов/расходов в основной валюте организации, дополнительные валюты отдельно, ниже — последние операции из `GET /ledger` с фильтром «Все/Доходы/Расходы». Журнал не называется полной историей платежей: он описывает движения денег, не содержит отклонённые оплаты и сейчас ограничен серверной выборкой. Ручной доход/расход — действующие категории, положительная сумма, дата/время в timezone группы, необязательные описание и событие своей группы. Сумма передаётся в minor units через общую утилиту; после успешной записи баланс и журнал перечитываются. Нет оптимистического изменения баланса, редактирования или удаления ledger entries.

В обоих разделах предусмотрены loading, пустой результат, ошибка с повтором, 401 с входом, 403/404 без раскрытия данных и корректное поведение после refresh/back/forward. Ошибка сохранения оставляет форму открытой и значения введёнными. Для web используется обычный диалог, не Telegram SDK или haptics. На 1280/1440 px сохранена desktop-композиция, при узком viewport/200% zoom действия доступны без обрезания страницы. Поля подписаны, ошибки объявляются, клавиатурный фокус виден, статус не определяется только цветом.

## Проверка и порядок выполнения

1. До реализации обновить SDD-карточку 6.10.1. По red → green → refactor покрыть PostgreSQL-интеграционными тестами `listHistory` и route: tenant/role isolation, каждый статус, равные timestamps и границы страниц, фильтр, invalid query, отсутствие скрытых полей. Существующий pending endpoint должен сохранить свой контракт.
2. Проверить frontend: оба пункта навигации; загрузка, фильтры, пагинация и повтор; однократное действие; подтверждение отклонения; `payment.not_pending`; reset при смене группы; корректные суммы, валюты, даты, категории и неизменяемость журнала. После финансовой мутации данные берутся снова с сервера.
3. Пройти визуальный/функциональный browser smoke с реальными API на 1280/1440 px, узком окне и при 200% zoom, включая пустой/ошибочный список, заполненные данные, клавиатуру, owner/organizer и роль без права доступа. Сверить MVP-элементы с актуальными референсами, не копируя фиктивные значения и будущие функции.
4. Прогнать `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test` с PostgreSQL, `pnpm build`, применимый financial smoke, независимое review и CI задачи перед PR/merge в GitHub `main`. Эти проверки не заменяют Telegram-host QA, production smoke и общую приёмку R0.6.

## Не делать

Не добавлять онлайн-оплату, массовое подтверждение, новую операцию возврата, split/credits, сборы, отчёты, CSV-экспорт, фиктивные показатели, редактирование/удаление журнала, реконструкцию причин старых отмен или отдельный staging. Никакого продвижения `prod`/VPS до готовности полного кандидата R0.6 и релизного runbook.

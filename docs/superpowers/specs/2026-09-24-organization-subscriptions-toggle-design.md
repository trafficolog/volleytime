# Task 5.13.21 — переключатель абонементов организации

Дата: 2026-09-24. Основание: решения пользователя при проектировании R0.6, [карта референсов v2](../../design/2026-09-23-reference-v2.md), [SDD-карточка](../../tasks/5-13-21-organization-subscriptions-toggle.md). JSX и HTML задают визуальное направление, но не доменные правила.

## Цель и границы

Владелец организации может временно отключить абонементы, не удаляя планы, покупки, остатки и историю. При отключении новые продажи и выбор абонемента для новой записи недоступны; после повторного включения действующие неистёкшие остатки снова можно использовать. Существующие организации остаются с включёнными абонементами после миграции. Настройка одна для организации: отдельного переключателя на каждом событии в R0.6 нет. Все платные события следуют настройке организации.

Реализация отделяется от визуального обновления игрока: задача 5.13.21 создаёт серверное правило и минимально необходимую связь в текущем интерфейсе; 8.10.1 оформляет это состояние в Mini App игрока по v2, 8.10.2 — в интерфейсе организатора, 5.15.1 — в новом desktop-кабинете. Ни один из этих экранов не должен иметь собственную независимую копию настройки.

## Данные и права

- В `organizations` добавляется `subscriptionsEnabled: boolean NOT NULL DEFAULT true`. Миграция сохраняет поведение всех существующих организаций. Значение возвращается действующим `GET /api/organizations/:orgId` и доступно только в рамках уже проверенного членства.
- `PATCH /api/organizations/:orgId` принимает явный boolean; менять его может только владелец, как и остальные существующие настройки. Обновление фиксируется текущим журналом аудита организации. Отсутствие поля в PATCH не меняет настройку.
- В существующих настройках группы владелец видит переключатель с пояснением: отключение сохраняет уже купленные абонементы, но останавливает новые продажи и применение к новым записям. После сохранения интерфейс перечитывает серверное значение. Ошибка сохранения не меняет видимый подтверждённый статус.
- Desktop-настройки задачи 5.15.1 используют тот же API и те же права. Организатор без роли владельца не получает возможность менять значение ни через UI, ни через API.

## Правила при выключении

| Поверхность                    | Поведение                                                                                                                                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Новые планы и покупки          | Создание новых планов и покупка абонемента отклоняются сервером с предметной ошибкой. Существующие планы и покупки сохраняются.                                                                |
| Новая запись на событие        | Для платного события способ `subscription` не предлагается и отклоняется сервером. Наличные и перевод продолжают работать; бесплатная запись не меняется.                                      |
| Существующая запись            | Подтверждённая запись не меняется. Ранее оформленная очередь сохраняет выбранный способ и может продвинуться по прежним условиям; отмена возвращает списанную сессию по существующему правилу. |
| Игрок с действующим остатком   | Пункт «Абонементы» остаётся видимым. Экран показывает остаток, срок и историю, объясняет паузу; покупка и выбор абонемента для новой записи недоступны.                                        |
| Игрок без действующего остатка | Пункт «Абонементы» скрыт из навигации и карточек главной. Прямая ссылка на собственную историю или ожидающую покупку остаётся доступной, но не позволяет купить новый абонемент.               |
| Организатор                    | Раздел управления планами скрыт из основной навигации; настройки объясняют, почему абонементы недоступны. Никакой фиктивной per-event опции не добавляется.                                    |
| Повторное включение            | Существующие активные, неистёкшие остатки опять доступны для новых записей; архивные и истёкшие абонементы не оживают.                                                                         |

«Действующий остаток» означает `status=active`, `usedSessions < totalSessions` и отсутствие истечения срока на момент проверки. Наличие только pending, exhausted, expired или cancelled не удерживает пункт меню. Исторические данные не удаляются и остаются доступными по прямому разрешённому маршруту. Ожидавшая оплаты покупка может быть подтверждена после отключения: она становится частью сохранённого остатка, но не открывает возможность новой записи до повторного включения. Редактирование или архивирование уже существующего плана не создаёт новую покупку и остаётся под текущими правами владельца. При ошибке получения настройки клиент не предполагает, что абонементы включены: он не показывает CTA покупки или оплаты абонементом до получения подтверждённого состояния. Проверка сервера остаётся обязательной даже при скрытом контроле.

## Компоненты и потоки

Один серверный признак проходит через существующий слой организации, сервисы планов/покупки и записи, API, текущие настройки и проекцию Mini App. Критические запреты проверяются в сервисной транзакции, чтобы прямой API-вызов и устаревший клиент не обходили настройку. UI использует организацию, полученную через авторизованный API, а не localStorage или макетные значения. На смене организации состояние пересчитывается для нового `orgId`; остаток другой группы не открывает раздел в текущей.

Текущий компонент формы события не содержит выбора способа оплаты или per-event флага. Задача не добавляет их: если организация отключила абонементы, событие не сможет принимать новые записи с этим методом. В задаче 8.10.2 форма события может пояснить это состояние, не вводя новое доменное поле.

## Ошибки и проверка

TDD начинается с тестов схемы и сервисного запрета: новая организация и мигрированная организация имеют значение `true`; владелец может выключить/включить, другой участник — нет; без поля PATCH статус не меняется; запрет покупки/создания плана/новой записи действует при `false`; наличные, перевод и бесплатное событие не затронуты. Отдельные тесты фиксируют сохранность существующих планов, активного остатка, подтверждённой записи, очереди, возврата сессии при отмене и восстановление доступности после включения. API-тесты подтверждают предметный отказ для прямых запросов.

UI-тесты покрывают матрицу: включено; выключено с действующим остатком; выключено без него; pending без активного остатка; смена группы; загрузка/ошибка настройки; отказ сохранения. Затем — пять обязательных gates, визуальный smoke 320/390 px в светлой и Telegram-тёмной темах, и отдельная реальная Telegram QA в 8.10.3. Репозиторные тесты сами по себе не закрывают Telegram или production acceptance.

## Вне задачи

Удаление или возврат стоимости купленных абонементов, индивидуальная настройка каждого события, несколько мест в одной записи, деление суммы, онлайн-оплата, будущие напоминания и автоматизация.

# R0.7: фиксированная цена и деление общей суммы события

Дата: 2026-10-01. Статус: спецификация и [письменный план реализации](../plans/2026-10-01-event-split-pricing.md) утверждены пользователем 2026-10-01; карточки `todo`, продуктовая реализация не начата. Версия: `v0.1.7`, расширение R0/MVP. База: GitHub main `2c85171c5cadcd1e1961341c190e066560005b13`; production-кандидат R0.6 остаётся `967aff312f962196e7347cc0e50f879f25f6dffa`.

## Цель и основание

Пользователь подтвердил реализацию выбора «Фиксированная цена / Делим сумму» после обнаружения его отсутствия в production. Организатор выбирает режим при создании события в Mini App и desktop. В split задаёт общую сумму; игрок видит прогноз, а после закрытия записи — свой точный платёж. Референсы: `references/screens-organizer.jsx` (форма и управление оплатами), `screens-web-forms.jsx` (форма), `screens-web.jsx` (состав/расчёт), `screens-player.jsx` (прогноз/итог). Это реальные файлы в `D:\ai\freelance\volleyball-volleytime\references`, обновлённые 2026-09-25. Макеты задают композицию; эта спецификация задаёт финансовые правила.

R0.6 исключал split по согласованной MVP-границе. Новое решение расширяет её отдельным R0.7; исторические критерии 8.10.2 не переписываются. Ручная Telegram/pilot приёмка R0.6 остаётся открытой и не закрывается созданием новых карточек.

## Рассмотренные варианты

1. **Рекомендуемый: расчёт один раз при ручном закрытии записи.** Прогноз меняется вместе с составом; окончательные доли и платежи появляются одной транзакцией. Соответствует ключевому потоку макета и существующим операциям подтверждения денег.
2. Пересчитывать уже созданные платежи при каждой записи/отмене. Сумма могла бы измениться после перевода денег; потребуются доплаты/возвраты и новый финансовый процесс. Для MVP не выбирается.
3. Сразу делить общую сумму на вместимость. При неполном составе касса не достигнет цели; это фиксированная цена с другим способом ввода, не запрошенный режим.

Закрытие только ручное. Автоматическое закрытие по времени относится к отдельной автоматизации. В UI существующий дедлайн отмены нельзя подписывать как время автоматического распределения.

## Предлагаемые продуктовые правила

- Одно место на одного игрока, как сейчас. Multi-seat из макета не включается в это расширение.
- Режим по умолчанию `fixed`; все старые события остаются фиксированными, включая бесплатные.
- Для `fixed` сохраняется прежняя цена за место, наличные/перевод, бесплатная запись и абонементы по настройке организации.
- Для `split` задаётся положительная общая сумма в валюте организации. Наличные/перевод выбираются при записи; абонемент, online и `free` сервер отклоняет независимо от видимости UI.
- Пока запись открыта, занявшая место бронь имеет `pending_payment`, но `paymentId=null`: место занято, сумма ещё не зафиксирована. UI и уведомления показывают «В составе · сумма после закрытия записи». Денежная очередь содержит только существующие платежи; такую бронь нельзя подтвердить как оплаченную.
- Для прогноза используются занятые места, без waitlist и отменённых записей. При нулевом составе показывается «При полном составе — …» с расчётом по вместимости; деления на ноль нет. Прогноз имеет знак `≈` и пояснение, что это не окончательная сумма.
- Кнопка «Закрыть запись и распределить» доступна active owner/organizer для опубликованного split-события, в том числе после начала, если оно ещё не отменено/не завершено. В диалоге — текущий состав и общая сумма; сервер перечитывает их под блокировкой.
- При закрытии фиксируются только брони, реально занявшие место на момент транзакции. Waitlist не получает платёж. При пустом составе закрытие отклоняется без изменения статуса.
- Делим в целых копейках. Каждому `floor(total / N)`, а остаток по одной копейке первым броням в порядке `bookedAt, id`. Разница не больше одной копейки, сумма всех долей точно равна цели. Пример: 100,00 BYN / 3 → 33,34 + 33,33 + 33,33. UI поясняет возможную разницу в одну копейку и показывает игроку именно его долю. Если общая сумма меньше N копеек, распределение отклоняется; нулевые платежи не создаются.
- Закрытие фиксирует состав, доли и платежи. Повторный запрос возвращает уже существующий результат, даже после подтверждения/отклонения платежа; новые платежи, audit-записи и уведомления не создаются.
- После фиксации игрок самостоятельно выйти из оплачиваемого состава не может. Организатор может снять бронь/отклонить её платёж по существующим правилам. Доли остальных остаются прежними, повторного распределения и повышения сумм нет. Недобор цели становится видимым в сводке. Waitlist после закрытия не продвигается.
- Снятие организатором не означает автоматический возврат уже подтверждённых денег: сохраняется действующее правило MVP. Полная отмена события возвращает подтверждённые split-платежи через существующий ledger, включая ранее снятую бронь с сохранённой allocatedAmount, отменяет pending, не создаёт новых начислений. Выбор только активных броней для такого возврата недостаточен. Нельзя повторно начислить или вернуть один платёж.
- Режим оплаты можно поменять только пока у события вообще не было броней. Общую split-сумму можно менять до распределения, под той же блокировкой события. После фиксации сумма, режим и состав расчёта неизменны; статус `published` через PATCH не может открыть split повторно. Остальные допустимые поля редактируются по текущим правилам.
- Прогноз читается из текущего ответа API. Обновление экрана или смена состава подтягивает новый прогноз; отдельный realtime-канал и автоматическая рассылка каждого колебания цены не добавляются.

Эти правила утверждены пользователем 2026-10-01: округление копеек, ручное закрытие, блокировка самостоятельного выхода после расчёта и отсутствие перераспределения после снятия организатором. Они не были явно определены прежним MVP.

## Модель и совместимость

Добавить к `events`: `priceMode` (`fixed|split`, default fixed), nullable `targetAmount` в minor units, nullable `pricingSettledAt` и nullable `pricingParticipantCount`. К `bookings`: nullable `allocatedAmount` в minor units. Суммы проходят integer/range validation до PostgreSQL (`0..2147483647` для fixed, `1..2147483647` для split).

Ограничения: fixed не содержит split-метаданные; split имеет положительный target и `price=0` (поле price относится только к fixed); settledAt/count либо оба null, либо оба заполнены, count положителен; allocatedAmount при наличии положителен. Миграция аддитивная, старые записи получают fixed без пересчёта. Доли после settlement сохраняются даже при cancelled/refunded для проверки исторической суммы; повторная активация таких броней запрещена.

Новая nullable колонка не требует менять fixture каждого старого fixed-события. Новые потребители проверяют mode до прежней ветки `price===0`; split никогда не трактуется как бесплатное событие. Между task PR в main создание split остаётся закрытым: серверная `EVENT_SPLIT_PRICING_ENABLED` включена только при точном значении `true`, по умолчанию false. Несекретная capability в ответе организации сообщает UI возможность создания; сервер отдельно проверяет её в POST и переходе mode в PATCH. Флаг ограничивает создание новых split-событий, но не блокирует обработку уже существующих. В Actions env он передаётся из одноимённой repository variable; включается только после готовности всех зависимых задач и release gate. Unit/integration fixtures явно включают capability для проверяемых split-сценариев.

Не нужны новый ledger, платёжный провайдер или таблица начислений: event хранит метаданные фиксации, booking — собственную фиксированную долю, существующие payments — начисление/статус денег. Ledger увеличивается только при настоящем подтверждении платежа, не при распределении.

## API и транзакции

Create/update принимают mode/target с перекрёстной валидацией. Старый body без mode сохраняет fixed. API не разрешает клиенту задавать settledAt/count/allocatedAmount, начислять произвольную сумму или менять валюту события.

Новый manager-only `POST /api/organizations/:orgId/events/:eventId/settle` вызывает сервис расчёта в одной PostgreSQL-транзакции. Порядок: проверить организацию/роль → захватить `pg_advisory_xact_lock(eventId)` → перечитать и заблокировать event → проверить mode/status/существующий settlement → выбрать текущий состав → рассчитать целые доли → создать и связать ровно один pending payment каждой брони → записать allocatedAmount/count/time и `closed` → audit → commit. Коллектор уведомлений отправляется после успешного коммита.

Возвращаются событие и summary: распределённая сумма, число участников, диапазон долей. Для игрока существующий GET события возвращает только его allocatedAmount/состояние оплаты и общий прогноз; чужие личные платежи не раскрываются. Public roster не помечает split-бронь оплаченной по одному статусу брони: требуется реальный succeeded payment. Для closed split общая доля выводится диапазоном при округлении; личная — точным amount.

Manager-only GET события возвращает `pricingPermissions: { canChangePriceMode:boolean; canChangeTargetAmount:boolean; canSettle:boolean }` для active owner/organizer своей организации. Mode permission определяется отсутствием ЛЮБОЙ истории booking, включая cancelled-only и waitlist-only, с existing role/state policy; текущий participantCount не доказывает отсутствие истории. Target permission — unsettled split с existing role/state policy; settle permission — active manager и published unsettled split. Capability отдельно ограничивает создание/переход в split. Игроку/чужой организации manager projection не выдаётся. Оба organizer parents Mini App/desktop используют эти серверные разрешения для формы и кнопки; сервер повторно проверяет историю/роль/status под event lock при mutation. Task 6.11.1 производит GET projection, Task 5.16.2 доказывает API-to-form cancelled-only/waitlist-only сценарии на обеих поверхностях.

Book, rebook, cancel, promotion, изменение target/mode и settle используют тот же event lock и перечитывают цену/статус после захвата. Операция, победившая в гонке до settle, входит в состав; операция после settle получает отказ/фиксированный результат. Подтверждение, отклонение, полная отмена и attendance сохраняют согласованный lock order. Никакой цикл event→payment / payment→event не вводится.

Обычный PATCH split `status=closed` запрещён: он не может обойти начисление. Split `finished` до settlement также запрещён. Attendance возможна только для оплаченной брони после начала; unsettled pending_payment нельзя отметить как оплату/посещение.

Ошибки: неверный режим/сумма, пустой состав, слишком малая сумма, изменённый статус/режим, запрещённое повторное открытие, неразрешённый метод, запрещённая самостоятельная отмена после фиксации. UI показывает actionable error и GET-повтор; неожиданные ошибки откатывают всю транзакцию без частичного закрытия или платежей.

## Уведомления

До закрытия: подтверждение занятого места и уведомление о повышении из waitlist содержат «Точная сумма после закрытия записи», без «Бесплатно» и без требования оплатить прогноз. После settlement: отдельное уведомление игроку с его точным amount, методом и действующим deep link события. Организатор получает одну сводку о распределении; создание N платежей не должно отправлять ему N одинаковых уведомлений о расчёте. Прежние уведомления реального confirm/reject/cancel сохраняются.

Ошибка Telegram-доставки после commit не меняет начисления; итог всегда доступен через API/UI. Повторный POST settle не рассылает заново. Гарантированная доставка через transactional outbox, очередь повторов и автоматизация не заявляются этой задачей.

## Интерфейсы

Общая форма Mini App/desktop: доступный выбор двух режимов в стиле референса, условное поле цены или общей суммы, валюта организации, прогноз при полном составе и пояснение об абонементах. Смена режима в несохранённой форме сохраняет отдельно введённые значения. На сервер уходит только соответствующий режиму набор данных. Кнопки/поля соблюдают уже принятые radio, focus, gray-card boundaries и отсутствие синих декоративных теней.

Управление событием в обоих интерфейсах: режим, общая сумма, состав, прогноз; после фиксации — итог/count/time и реальные collected/pending/cancelled/refunded суммы без смешивания валют. Отдельная кнопка ручного закрытия с подтверждением, блокировка повторных нажатий, проверка live route до POST и после ответа. Старые данные другой группы не показываются во время смены маршрута или ошибки.

Игрок: карточки, event page, booking confirmation, «Мои записи» и Home согласованно показывают прогноз или собственный итог. Выбор абонемента скрыт и запрещён сервером именно для split-события; глобальная настройка организации не меняется. До фиксации нет ложных «Оплачено»/«Бесплатно» или требования оплатить приблизительную сумму.

Полная анонимная публичная страница и event QR/share-link отсутствуют в подтверждённом MVP. Новый режим охватывает существующий доступный участникам roster и действующие deep links; отдельную публичную страницу этим расширением не добавляем. Лендинг после готовности backend/UI может показывать реальный split в применимых сохранённых блоках исходника; до этого действующие обещания не меняются.

## Проверка и выпуск

Тесты расчёта: 10000/3, точное деление, N=1/500, одинаковое bookedAt с id, max integer, empty/target<N, отсутствие float-расхождения. PostgreSQL: no payment до фиксации, точная сумма начислений, неизменный ledger до confirm, повторный/concurrent settlement, отмена/запись/повышение/target edit одновременно с закрытием, confirm/reject/cancel события, отказ другой организации/роли, late response после route switch, fixed/free/subscription regression.

Browser QA: формы/управление/игрок Mini App320/390 light/dark, desktop1280 light/dark, клавиатура, focus, 200% reflow для новых контролов, реальное поведение API, error/retry и stale routes. Прежние проверки пользователя сохраняются для неизменённых экранов; новая функциональность имеет своё доказательство.

Production: пять gates + CI выбранного SHA + review → main → reviewed fast-forward prod → GitHub Actions image-bundle с проверенным dump до миграций → exact Git/images/runtime/health SHA и synthetic smoke → реальные два Telegram-аккаунта в pilot organization: запись, изменение прогноза, ручное закрытие, точное уведомление, confirm/reject, абонемент недоступен, повторное закрытие не дублирует деньги.

Аддитивная миграция совместима со старой схемой чтения, но старый код трактует split.price=0 как бесплатно. Поэтому после создания первого split-события rollback на R0.6 бизнес-логически небезопасен. Existing image labels/build SHA и data preflight сохраняются; ранний запрос без split не разрешает fixed-only downgrade. Под existing deploy lock перед AUTHORITATIVE guard захватить точные active web/bot container IDs и images, остановить все project web/bot writers (включая duplicate/scaled) и доказать отсутствие running writers. Stop завершает или прерывает in-flight транзакции; только затем query schema/split rows через existing postgres Compose service. До authoritative guard не менять Git/manifest/env и не активировать images. Повторить проверку отсутствия writers непосредственно перед switch и удерживать quiescence до old runtime activation. Это краткая контролируемая пауза rollback, без нового persisted feature table/global advisory lock и без паузы обычных flows.

Query error или несовместимость images запрещают downgrade. До stop отказ сохраняет runtime; после stop восстановить только захваченные совместимые current containers/images, никогда unsafe old fallback; при невозможности доказать safe recovery сообщить точный state для reviewed roll-forward. Manual и automatic migration/activation/smoke recovery соблюдают одну границу. Тесты доказывают: in-flight split до stop либо commit до authoritative query (old runtime rejected), либо rollback; новый split не commit между guard и old activation. При отсутствии новой схемы/split допускается предыдущий fixed-only образ только с удерживаемой quiescence. После первого split — восстановление совместимого нового кандидата или reviewed roll-forward. Нельзя удалять split-данные, менять платежи или восстанавливать БД ради обхода этой границы.

# Task 21.2.11: Способы оплаты группы: реквизиты (`W-11`)

## Цель

Организатор включает способы оплаты группы и задаёт реквизиты (перевод на карту, наличные); игрок видит их при оплате места.

## Контекст

- Решение владельца 2026-10-15 (ревью PR #138, 20.5.7): часть макета W-11, которой нужна новая серверная работа, выделена из [20.5.7](20-5-7-settings.md) отдельной задачей v0.3.0; в v0.2.0 она не входит.
- Спецификация референса: [W-11 · Настройки](../design/reference-v3/specs/03-organizer-web/W-11-settings.md); макет: 4 Кабинет организатора → Настройки → Способы оплаты, `4-cabinet/21-screen.png`; исходник — `WebSettings` в `handoff/screens-web.jsx`.
- **Как есть (main `35a43fd`):** В настройках группы нет способов оплаты; игрок платит по реквизитам, которые организатор присылает вручную. Онлайн-оплата не реализована (фаза 12).
- **Дельта до референса:** Список способов: «Наличными организатору» (касса обновляется после подтверждения), «Перевод на карту» с реквизитами (банк, последние цифры, получатель); «ЕРИП» и «Картой онлайн (bePaid)» показаны недоступными (фаза 12); переключатели включения; реквизиты показываются игроку в состоянии «ожидает оплаты».
- Модель: реализация `claude-sonnet-5-5`, ревью `claude-opus-5-5` (ревью Opus: деньги, платёжные реквизиты и доступ); маршрутизация — [ORCHESTRATION](../ORCHESTRATION.md).

## Что должно быть сделано

1. Модель и API: способы оплаты группы (тип, включён, реквизиты) с чтением и записью только для ролей owner/organizer по [матрице прав](../architecture/permissions-v3.md); миграция forward-compatible, схема и контракт — по [ADR 19.2.1](19-2-1-domain-model.md) первым шагом.
2. Хранение реквизитов: показывать игроку банк, маску карты (последние 4 цифры) и получателя; полный номер карты не хранить и не отдавать (если нужен — остановиться и вернуть задачу оркестратору).
3. Подраздел «Способы оплаты» в кабинете: переключатели, форма реквизитов с подсказкой влияния, недоступные способы с пояснением «фаза 12».
4. Выдача включённых способов и реквизитов участникам группы для экрана оплаты в Mini App ([20.4.5](20-4-5-event-booking.md)); подтверждение платежа и проводка в кассу — как в [21.2.3](21-2-3-cashbox.md), без изменений.
5. Сверить экраны с референсом через харнесс [19.0.2](19-0-2-visual-reference-harness.md) и приложить отчёт к PR.

## Критерии приёмки

- ✅ Выключенный способ не показывается игроку; при выключении всех способов экран оплаты объясняет, как заплатить
- ✅ Реквизиты видят только участники этой группы; tenant safety и IDOR-тесты на чтение и запись (чужая группа, роль игрока)
- ✅ Изменение реквизитов пишется в журнал аудита с автором
- ✅ Тесты: валидация реквизитов, права ролей, отсутствие полного номера карты в ответах API и логах, компонентные на подраздел
- ✅ Отчёт визуальной сверки по экранам из `reference.screens` без открытых расхождений Critical/Important
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important

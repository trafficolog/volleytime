# Task 21.2.18: API обзора кабинета: статистика группы и касса за 4 недели

## Цель

Дать обзору кабинета (W-02) реальные данные уровня группы, которых нет в ответе дашборда.

## Контекст

- Решение владельца 2026-10-27 ([журнал](../operations/decisions/2026-10-12-reference-v3-decisions.md), «Разделение 21.2.1»): исполнитель 21.2.1 остановился, потому что макет W-02 показывает цифры группы, которые `GET /api/organizations/[orgId]/dashboard` (`apps/web/server/api/organizations/[orgId]/dashboard.get.ts`) не возвращает. Серверная часть выделена в эту карточку, визуальная остаётся в [21.2.1](21-2-1-overview.md).
- **Как есть:** дашборд отдаёт игроку ближайшие записи и абонемент, управляющему — деньги и ближайшие события (8.8.12); кнопка создания события и блок «Касса группы» уже есть (20.5.5, `done`).
- **Дельта:** недостающие агрегаты для W-02: события в этом месяце; записи и заполняемость в процентах; активные абонементы по группе; полный список ожидающих оплат с суммами по строкам; ряд «Касса за 4 недели» (по неделям).
- Касса за 4 недели считается по тому же источнику, что касса кабинета ([21.2.3](21-2-3-cashbox.md)) и поступления сборов ([21.2.4](21-2-4-collections-domain.md), подтверждённый взнос → ledger `contribution`), чтобы цифры обзора, кассы и сборов сходились (DoD фазы 21, п. 2).
- Модель: реализация `claude-sonnet-5-5`, ревью `claude-opus-5-5` (ревью Opus + тесты граничных случаев; деньги и доступ — правила 1–2 [ORCHESTRATION](../ORCHESTRATION.md)).

## Что должно быть сделано

1. В `packages/core` добавить агрегации для управляющего: число событий месяца (по часовому поясу группы), записи и заполняемость %, число активных абонементов группы, список ожидающих оплат (игрок, событие, сумма, давность) с общей суммой, ряд кассы за 4 недели (недели по часовому поясу группы, поступления без отменённых и возвращённых записей по правилам кассы 21.2.3).
2. Расширить ответ `dashboard.get.ts` новыми полями для управляющего; формат и типы — в `packages/shared`, обратная совместимость: существующие поля не меняются, игроку новые поля не отдаются.
3. Авторизация остаётся прежней: org-scoped, участник группы; агрегаты группового уровня и деньги — только управляющему (`canManageContent`), без доступа к чужим группам.
4. Тесты (RED→GREEN): граничные дни месяца и границы недель, часовой пояс группы, пустая группа, отменённые и возвращённые записи, сходимость ряда кассы с суммой кассы 21.2.3, IDOR (игрок и участник другой группы не получают агрегаты).
5. Миграция не планируется: агрегаты считаются по существующим таблицам. Если окажется, что нужна миграция (индекс или новая колонка), исполнитель останавливается и возвращает карточку оркестратору (ADR и ревью Opus по ORCHESTRATION, правило 3).

## Критерии приёмки

- ✅ Ответ дашборда содержит для управляющего все пять наборов данных W-02; для игрока ответ не меняется
- ✅ Ряд «Касса за 4 недели» сходится с кассой кабинета и поступлениями сборов
- ✅ Игрок и участник другой группы не получают групповые агрегаты (IDOR-тесты)
- ✅ Схема и миграции не изменены
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important
- ✅ RED→GREEN тесты на граничные случаи, деньги/доступ приложены к PR

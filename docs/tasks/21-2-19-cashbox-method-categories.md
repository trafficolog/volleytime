# Task 21.2.19: Касса: способ оплаты ручной записи и категории Мячи/Судья/Тренер

## Цель

Довести форму ручной операции и журнал кассы до макета W-07: способ оплаты записи и дополнительные категории расходов.

## Контекст

- Решение владельца 2026-10-27 ([журнал](../operations/decisions/2026-10-12-reference-v3-decisions.md), «Касса кабинета: месяц и ручная запись»): переключатель «Наличные / Перевод» экрана `4-cabinet/10` и категории «Мячи», «Судья», «Тренер» требуют миграции и вынесены из [21.2.3](21-2-3-cashbox.md) в эту карточку. Плитки «Поступило» и «Списано» кабинета показывают выбранный месяц, баланс — за всё время, Mini App — за всё время (то же решение; в эту карточку не входит).
- **Как есть:** записи кассы (ledger) хранят категорию и комментарий; способа оплаты у ручной записи нет; категорий «Мячи», «Судья», «Тренер» нет.
- **Миграции сериализуются** ([ORCHESTRATION](../ORCHESTRATION.md#параллельность)): эта карточка берёт следующий свободный номер после миграции [21.2.4](21-2-4-collections-domain.md) (ожидается `0033`) и перегенерирует миграцию после rebase на `main`, если порядок сменился. В работе одновременно только одна задача со схемой.
- Модель: реализация `claude-sonnet-5-5`, ревью `claude-opus-5-5` с тестами; деньги и доступ — правила 1–2 ORCHESTRATION.

## Что должно быть сделано

1. Схема: nullable-колонка способа оплаты в записях ledger (значения `cash` / `transfer`; у прежних записей и записей, созданных не вручную, остаётся `NULL`) и новые значения категории расходов «Мячи», «Судья», «Тренер»; аддитивная миграция, forward-compatible по deploy runbook.
2. Откат миграции: `packages/db/rollback/<номер>_*.sql` с предохранителем по практике репозитория (отказывает, пока есть записи с заполненным способом оплаты или с новыми категориями, чтобы не потерять данные) и контрактный тест скрипта.
3. Quiescent-guard отката приложения (`scripts/verify-split-rollback.sh`, capability-labels образа): оценить, неверно ли прежний runtime читает записи с новыми категориями или способом. Если прежний runtime падает или искажает данные — добавить capability и запрос «есть записи с новой категорией или способом» по образцу существующих (`capability_names`, `capability_rows`) и поправить раздел deploy runbook; если нет (nullable-колонка игнорируется, категория безопасно отображается) — записать вывод и обоснование в PR и карточку, guard не менять.
4. API кассы: ручная запись принимает способ оплаты и новые категории (валидация, права, аудит прежние); список и сводка возвращают способ.
5. Кабинет: в форме ручной операции переключатель «Наличные / Перевод» (макет `4-cabinet/10`), категории «Мячи», «Судья», «Тренер» в выборе; в журнале колонка способа оплаты; в выгрузке CSV колонка способа.
6. Mini App не меняется, кроме необходимого для отображения новых категорий без ошибок (если запись с новой категорией попадает в Mini App организатора).
7. Тесты (RED→GREEN): создание с каждым способом и без него, отказ при недопустимом значении, права и IDOR, новые категории в сводке, CSV, откат миграции с данными и без. Сверка экранов 19.0.2 по `reference.screens`.

## Критерии приёмки

- ✅ Ручная запись сохраняет способ оплаты и категорию «Мячи» / «Судья» / «Тренер»; прежние записи читаются без изменений
- ✅ Журнал и CSV показывают способ оплаты; суммы кассы не меняются
- ✅ Миграция аддитивна; откат отказывает при наличии новых данных; решение по quiescent-guard зафиксировано
- ✅ Игрок и участник другой группы не создают и не видят записи кассы (IDOR-тесты)
- ✅ Отчёт визуальной сверки по `4-cabinet/09`, `10` без открытых расхождений Critical/Important
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important; RED→GREEN тесты приложены

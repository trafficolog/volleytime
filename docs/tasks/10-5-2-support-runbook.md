# Task 10.5.2: Support-runbook (типовые проблемы, эскалация)

## Цель

Runbook поддержки беты: типовые проблемы и реакция, каналы (чат беты, feedback-кнопка, Sentry, UptimeRobot), эскалация, SLA беты.

## Контекст

Решение 6: системная поддержка, не по памяти. Соло-ведение — нужен чёткий процесс реакции. Источники проблем: чат беты, feedback-кнопка (10.2), Sentry (9.6 ошибки), UptimeRobot (9.6 downtime).

## Что должно быть сделано

1. **Runbook `docs/operations/runbooks/beta-support.md`:**

   ```markdown
   # Поддержка беты

   ## Каналы поступления проблем

   - Чат беты (Telegram) — живые вопросы организаторов
   - Feedback-кнопка (10.2) → служебный канал
   - Sentry — исключения (web+bot)
   - UptimeRobot — downtime alert

   ## Приоритизация (severity)

   - **P0 Blocker:** платформа недоступна, нельзя записаться/оплатить, потеря данных
     → реакция немедленно, hotfix
   - **P1 Major:** важный сценарий сломан у организатора, но есть обходной путь
     → в течение дня
   - **P2 Minor:** косметика, неудобство, edge case
     → backlog, по возможности

   ## Типовые проблемы и реакция

   | Проблема                 | Диагностика                                    | Решение                              |
   | ------------------------ | ---------------------------------------------- | ------------------------------------ |
   | Mini App не открывается  | Telegram версия, BotFather domain, Caddy/HTTPS | проверить /health, логи caddy        |
   | Не приходят уведомления  | bot жив? internal notify? telegram_id есть?    | логи bot, Sentry, проверить notifier |
   | Запись не проходит       | capacity, deadline, membership, concurrency    | логи web, проверить событие          |
   | Оплата не подтверждается | payment status, права организатора             | super-admin обзор, логи              |
   | Игрок не видит событие   | published? org membership?                     | проверить статус события             |

   ## Эскалация

   - P0 → бросить всё, hotfix + сообщить организаторам в чат беты
   - Данные/деньги → особая осторожность, проверить ledger/payments перед действиями
   - Если нужен откат → disaster recovery runbook (9.7.2)

   ## SLA беты (ориентир, не обязательство)

   - P0: часы
   - P1: день
   - P2: best effort

   ## Коммуникация

   - При P0/P1 — сообщить затронутым организаторам в чат беты (прозрачность)
   - После фикса — подтвердить решение, спросить подтверждение у организатора
   ```

2. **Связь с мониторингом (9.6):** Sentry/UptimeRobot alerts → как реагировать (где смотреть, что проверять).

3. **Связь с recovery (9.7.2):** при P0 с данными — ссылка на disaster recovery.

## Подсказки

- **Severity-триаж экономит нервы** — не всё P0. Чёткие уровни → понятно что бросать всё, что в backlog.
- **Типовые проблемы из Трека B** — ты уже видел где спотыкаются. Документируй диагностику, чтобы не вспоминать каждый раз.
- **Данные/деньги — особая осторожность** — ledger/payments append-only, но действия в поддержке могут навредить. Проверять перед вмешательством.
- **Прозрачность с организаторами** — бета-участники лояльны, но ценят коммуникацию. Сообщать о проблемах/фиксах укрепляет доверие.

- ❌ Не давать жёстких SLA-обязательств (бета, соло)
- ❌ Не действовать с данными/деньгами без проверки
- ❌ Не молчать при P0/P1 (коммуникация)

# Task 5.15.1: Desktop-кабинет организатора v2

## Цель

Сделать рабочий desktop-интерфейс для MVP-потоков организатора по `4 Кабинет организатора.html`.

## Контекст

Сейчас основные маршруты организатора живут в `/m`; отдельного responsive desktop-shell нет. [Карта v2](../design/2026-09-23-reference-v2.md) отделяет desktop MVP от будущих разделов.

## Что должно быть сделано

1. Построить desktop-shell с навигацией и маршрутизацией, переиспользуя текущие auth/API/права и не дублируя доменную логику.
2. Реализовать dashboard, события (список/календарь/деталь/форма), состав, абонементы и MVP-настройки организации по v2.
3. Покрыть доступ organizer/owner, пустые/ошибочные состояния, реальные действия и responsive переход в узком viewport тестами.
4. Desktop-настройка абонементов использует тот же API и owner-only право из 5.13.21; при отключении раздел планов скрыт из основной навигации без удаления данных.

## Критерии приёмки

- Организатор выполняет перечисленные операции через desktop без Mini App; игрок не получает административный доступ.
- Данные общие с Mini App; тесты подтверждают отсутствие расхождения статусов и прав.
- Пять gates зелёные, визуальный smoke desktop 1280/1440 px.

## Подсказки

- `/m` остаётся Telegram-first; desktop создаётся как отдельная оболочка над теми же API.
- QA 2026-09-27: в обзоре hero «Касса группы» на 1440 px получился чёрным вместо синего `--vt-blue-ink` из `4 Кабинет организатора.html`. Исправить в этой задаче с RED→GREEN проверкой вычисленного CSS-цвета.

## Находки финального review 2026-09-27

- Архивная организация отвечает HTTP 410, а desktop-shell показывает общую ошибку с повтором. Добавить отдельное состояние `archived` и прямой browser smoke.
- После успешного PATCH/POST настроек вторичный `fetchAll()` может упасть и показать ложное сообщение о провале мутации; подтверждённый сервером результат должен оставаться успехом, архивирование — вести к выбору групп.
- Запоздалые ответы на `/app` и форме создания организации не должны навигировать после ухода с маршрута.
- Ошибка загрузки приглашений должна иметь retry и не сочетаться с пустым состоянием.
- По каждому пункту: сначала RED unit/browser проверка, затем минимальное исправление и GREEN; после этого повторить пять gates и review изменённого участка.

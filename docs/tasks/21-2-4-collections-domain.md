# Task 21.2.4: Сборы: домен, API и касса

## Цель

Серверная модель сборов вне событий: сбор, взносы, подтверждение, попадание в кассу.

## Контекст

- Задача добавлена оркестратором при перепланировании v3: в списке задач референса её нет, но она нужна для экранов или выпуска.
- **Как есть (main `e68acf2`):** Только категория ledger `contribution` (ручной доход). Фаза 11 — скелет.
- **Дельта до референса:** Новый домен.
- Модель: реализация `claude-opus-5-5`, ревью `claude-opus-5-5` (ревью Opus + тесты граничных случаев и гонок); маршрутизация — [ORCHESTRATION](../ORCHESTRATION.md).

- **Уточнения реализации (исполнитель, 2026-10-27; по ADR v3, без новых решений владельца):**
  - Прежний runtime (v0.2.0) подтверждает ожидающий взнос как `payment_income` («Оплата абонемента»), поэтому по правилу совместимости 4 ADR создание сборов и взносов — за флагом `COLLECTIONS_ENABLED`, образы несут `org.volleytime.collections`, guard отката приложения (`scripts/verify-split-rollback.sh`) отказывает, пока есть ожидающие взносы. Проводка флага в Deploy (`deploy.yml`) — релизная 21.3.1 (workflow в этой задаче не меняется).
  - Маршруты по матрице прав: `GET/POST …/collections`, `GET/PATCH …/collections/{id}`, `POST …/{id}/complete`, `POST …/{id}/cancel`, `POST …/{id}/contributions`, `POST …/contributions/{contributionId}/confirm|reject`; удаления сбора нет (матрица его не задаёт; сбор со взносами защищён FK).
  - Одно ожидающее обещание игрока в сборе.
- **Решения владельца (2026-10-28, [журнал решений](../operations/decisions/2026-10-12-reference-v3-decisions.md)):**
  - Повторный взнос до подтверждения — новая заявка: под блокировкой строки сбора прежний pending-платёж отменяется (запись `audit_log` `collection.contribution_replaced`) и создаётся новый; организаторы получают новую заявку; сумма ожидающего платежа никогда не меняется, устаревшее подтверждение или отклонение по старому id — 409 `payment.not_pending` (маршрут сбора и `POST …/payments/{id}/confirm`).
  - Дедлайн сбора — только отображение: сбор закрывает организатор вручную; автозакрытие по дедлайну возможно позже через планировщик (отдельной карточкой).
- При отмене сбора игроки с отклонёнными обещаниями получают уведомление `payment_rejected` (текст «Взнос в сбор … отклонён»).
- Проводка флага в Deploy, preflight миграции, проверка метки и guard на кандидате, включение флага — пункты 4–7 релизной [21.3.1](21-3-1-release-v0-3-0-qa.md).

## Что должно быть сделано

1. Схема и миграция по ADR 19.2.1
2. API: CRUD сбора (организатор), список и взнос (игрок), подтверждение/отклонение взноса
3. Подтверждённый взнос → ledger `contribution`; права и аудит
4. Integration-тесты, включая гонки подтверждения

## Критерии приёмки

- ✅ Сумма подтверждённых взносов = поступления кассы по сбору
- ✅ Игрок не видит сборы чужой группы (IDOR)
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important
- ✅ RED→GREEN тесты на граничные случаи, деньги/доступ и конкурентность приложены к PR

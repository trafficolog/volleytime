# Task 21.2.20: API статистики игроков: активность, абонемент, долг

## Цель

Дать экрану «Игроки» кабинета реальные цифры по каждому игроку: активность, абонемент, задолженность и статистику карточки.

## Контекст

- Решение владельца 2026-11-04 ([журнал](../operations/decisions/2026-10-12-reference-v3-decisions.md), «Кабинет «Игроки» (21.2.2)»): [21.2.2](21-2-2-players.md) строит экран на имеющихся данных; колонки «Активность», «Абонемент», «Задолженность» и статистика карточки игрока выделены сюда, потому что API участников их не отдаёт.
- Цифры должны совпадать с отчётами ([W-10 → 21.2.7](21-2-7-reports.md)) и Mini App организатора ([M-24 → 21.1.3](21-1-3-org-players-report.md)): один источник агрегатов, а не второй расчёт («Игроки и отчёты» — общий функционал, [links](../design/reference-v3/specs/links.md#reports)). Если 21.2.7 уже вынесла общий сервис в `packages/core`, использовать его.
- **Как есть:** список участников с ролью и уровнем; посещаемость, абонемент и долг по игроку в нём отсутствуют.
- **Дельта:** агрегаты по игроку и подключение колонок и статистики карточки на экране 21.2.2.
- Модель: реализация `claude-sonnet-5-5`, ревью `claude-opus-5-5` с тестами; деньги (долг) и доступ — правила 1–2 [ORCHESTRATION](../ORCHESTRATION.md).

## Что должно быть сделано

0. Умолчания (инженерные, журнал решений 2026-11-05): «посещение» — запись с отметкой `attended`; прошедшая запись, оставшаяся `confirmed`, не считается ни посещением, ни неявкой; расчёт посещаемости переиспользует `reportsService.getPlayerAttendance` — функцию посещаемости, которую добавляет карточка 21.2.7 ([PR #215](https://github.com/trafficolog/volleytime/pull/215), зависимость этой карточки); её нужно переиспользовать, второй расчёт не писать. До merge PR #215 в `main` её нет.
1. В `packages/core`: агрегаты по игроку группы за период — посещения, пропуски (no-show), доля посещаемости, дата последней активности («активность»), активный абонемент (остаток занятий, срок), задолженность (неоплаченные места прошедших и ожидающих событий, сумма и число). Источник посещений и долга — тот же, что у отчётов 21.2.7.
2. Расширить API списка игроков группы полями агрегатов (для управляющего); формат и типы в `packages/shared`; существующие поля не менять, игроку чужие агрегаты не отдавать. Пагинация и фильтры списка не должны деградировать (агрегаты считаются пакетно, без N+1).
3. Права: org-scoped, только управляющий группы (`canManageContent`); участник другой группы и обычный игрок не получают данные. Игрок видит о себе только то, что уже отдаёт его API.
4. Экран 21.2.2: колонки «Активность», «Абонемент», «Задолженность» и статистика в карточке игрока по данным API (вёрстка по `4-cabinet/06`); сверка 19.0.2.
5. Тесты (RED→GREEN): границы периода и часовой пояс группы, игрок без записей, отменённые и возвращённые места, освобождённое оплаченное место (`seat_released_at`), сходимость долга и посещений с отчётом 21.2.7, IDOR (игрок и управляющий другой группы), отсутствие N+1.
6. Миграция не планируется (агрегаты по существующим таблицам); если нужна — остановиться и вернуть карточку оркестратору (ADR и ревью Opus).

## Критерии приёмки

- ✅ Колонки и статистика карточки показывают данные API; цифры совпадают с отчётом 21.2.7 за тот же период
- ✅ Долг и абонемент считаются верно на граничных случаях (освобождённые места, возвраты, истёкший абонемент)
- ✅ Управляющий другой группы и игрок не получают агрегаты (IDOR-тесты)
- ✅ Схема и миграции не изменены
- ✅ Отчёт визуальной сверки по `4-cabinet/06` без открытых расхождений Critical/Important
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important; RED→GREEN тесты на деньги и доступ приложены

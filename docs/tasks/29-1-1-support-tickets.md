# Task 29.1.1: Обращения: модель, статусы и сроки

## Цель

Единая модель обращения в поддержку для игроков, тренеров, организаторов и посетителей без входа.

## Контекст

- Спецификация референса: [P-22 · Обращения: модель, статусы и сроки](../design/reference-v3/specs/01-platform/P-22-support-tickets.md); обновление референса — [отчёт 2026-11-24](../design/2026-11-24-reference-v3-update.md).
- Макет: 3 Mini App → Профиль → Помощь и поддержка; 4 Кабинет → Поддержка; 4b Root Admin → Поддержка; 10 База знаний → Написать в поддержку.
- **Как есть (main `69a5595`):** обращений в поддержку нет; обратная связь описана в 27.10.3 и 10.2.1–10.2.2 (поглощаются, D-29). Роли пользователя — `organization_members.role`, root — `users.is_root_admin`.
- **Дельта до референса:** всё, что в «Что должно быть сделано»; работающее не переписывается.
- Решения владельца: [D-29](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-29).
- Поглощает: [27.10.3](27-10-3-feedback-support.md), [10.2.1](10-2-1-feedback-endpoint.md), [10.2.2](10-2-2-feedback-ui.md).
- Модель: реализация `claude-opus-5-5`, ревью `claude-opus-5-5` (обязательны тесты граничных случаев); маршрутизация — [ORCHESTRATION](../ORCHESTRATION.md).

## Что должно быть сделано

**Шаги (правило 3 [ORCHESTRATION](../ORCHESTRATION.md#маршрутизация-моделей)):** контракт — `claude-opus-5-5`: схема и миграция обращений и сообщений, статусы и сроки (SLA в рабочих часах), сервис, API для пользователя и для команды платформы, IDOR- и ролевые тесты. UI — в 29.2.x и 29.3.x.

**Объём** (по спецификации)

- Обращение: номер S-NNNN, автор, роль автора, организация (если есть), тема, канал (Mini App, кабинет, бот, сайт помощи), статус, исполнитель
- Сообщения: автор, текст, время, тип — сообщение пользователя, ответ поддержки, внутренняя заметка, системное
- Статусы: новое → в работе → есть ответ (ждём пользователя) → решено; пользователь может вернуть «решено» ответом в течение 7 дней
- Сроки: первый ответ — 4 рабочих часа, считается по часам работы из R-14; флаг «близко к сроку» за 1 ч, «просрочено» после срока
- Автозакрытие: «есть ответ» без реакции 3 дня → «решено», бот предупреждает за сутки
- Обращения организации видят владелец и тот, кто создал; игрок видит только свои
- Каждая смена статуса и исполнителя пишется в журнал (R-07)

**Данные и API** (по спецификации; точные маршруты и имена — в контракте)

- POST /support/tickets
- GET /support/tickets?mine=1 · ?org={id}
- GET /support/tickets/{id}
- POST /support/tickets/{id}/messages
- POST /support/tickets/{id}/solve — пользователь закрывает сам
- PATCH /admin/support/tickets/{id} — статус, исполнитель, тема (root)

## Критерии приёмки

- ✅ Внутренняя заметка никогда не уходит пользователю и не видна в его API
- ✅ Счётчик срока не идёт вне часов работы
- ✅ Автозакрытие идемпотентно: повторный запуск задачи не шлёт второе предупреждение
- ✅ Номер обращения уникален и не меняется
- ✅ IDOR- и ролевые тесты на каждый новый эндпоинт
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` (обязательны тесты граничных случаев) без Critical/Important

## Подсказки

- Handoff: [README](../design/reference-v3/handoff/README.md) — статусная модель, токены, доменная логика.
- Сроки считаются в часах работы поддержки (R-14) в часовом поясе платформы; хранить `due_at`, а не пересчитывать на лету.
- Номер обращения `S-NNNN` — последовательность, не id строки.

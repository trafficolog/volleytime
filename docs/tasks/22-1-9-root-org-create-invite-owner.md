# Task 22.1.9: Приглашение владельца без аккаунта при ручном создании организации

## Цель

При ручном создании организации в Root Admin указывать владельцем человека, у которого ещё нет аккаунта: он получает приглашение и становится владельцем после входа.

## Контекст

- Решение владельца 2026-11-19 ([D-17](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-17)): приглашение выделено из [22.1.3](22-1-3-organizations.md) в отдельную карточку бэклога; релиз не назначен.
- Макеты: [4b-root-admin/03-screen.png](../design/reference-v3/screenshots/4b-root-admin/03-screen.png), [4b-root-admin/04-screen.png](../design/reference-v3/screenshots/4b-root-admin/04-screen.png); спецификация [R-01](../design/reference-v3/specs/04-root-admin/R-01-organizations.md).
- **Как есть:** ручное создание организации ([22.1.3](22-1-3-organizations.md)) назначает владельцем существующего пользователя; для пользователя без аккаунта пути нет.
- **Образец:** личная ссылка передачи владения ([D-15](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-15), [21.2.17](21-2-17-settings-transfer-delete-group.md)) — одноразовая, с истекающим сроком, привязанная к получателю; способы входа — [D-05](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-05).
- Задача касается доступа и ролей (owner): ревью `claude-opus-5-5` с IDOR-тестами (правило 2 [ORCHESTRATION](../ORCHESTRATION.md)).

## Что должно быть сделано

1. Определить в карточке до кода (с согласованием владельца): как указывается приглашаемый (email или Telegram), срок жизни приглашения, канал доставки (ссылка, которую root передаёт сам, или письмо), что происходит с организацией до принятия (без владельца, владелец-root, статус «ожидает владельца»), отмена и повторная отправка.
2. Серверная часть: приглашение создаётся вместе с организацией в одной транзакции; ссылка одноразовая, привязана к приглашённому, срок жизни ограничен; токен хранится хэшем и не попадает в журнал, ответы списков и логи.
3. Принятие: после входа приглашённый получает роль owner; чужой пользователь, просроченная, использованная или отменённая ссылка отклоняются без раскрытия данных организации.
4. Форма создания: способ выбора «существующий пользователь» или «пригласить по email/Telegram», отображение состояния «ожидает владельца» в списке и карточке организации.
5. Аудит платформы: создание, принятие, отмена и истечение приглашения.
6. Тесты: принятие нужным пользователем; чужой пользователь; повтор, истечение, отмена; гонка двух принятий; IDOR; доступ (401, 403).
7. Сверить экраны с референсом вручную (десктоп 1440x900 и мобильный 375x812, отчёт в теле PR) по [D-16](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-16).

## Критерии приёмки

- ✅ Организация создаётся с приглашением; приглашённый становится владельцем после входа и принятия, не раньше
- ✅ Ссылка одноразовая, привязана к получателю, не раскрывает данных организации чужим; токен не попадает в журнал и логи
- ✅ Отчёт визуальной сверки по экранам из `reference.screens` без открытых расхождений Critical/Important
- ✅ Пять gates CODING_STANDARDS на tested revision; ревью `claude-opus-5-5` без Critical/Important, включая IDOR

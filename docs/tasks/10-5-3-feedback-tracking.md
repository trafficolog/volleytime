# Task 10.5.3: Feedback-трекинг процесс

## Цель

Процесс фиксации и приоритизации обратной связи: как собирать (из чата, кнопки, сессий), категоризировать, связывать с задачами/фиксами, не терять.

## Контекст

Решение 6: feedback-трекинг. Обратная связь приходит из разных каналов (чат, кнопка 10.2, еженедельные сессии). Нужен лёгкий процесс, чтобы не терять и приоритизировать (что чинить/строить).

## Что должно быть сделано

1. **Runbook `docs/operations/runbooks/beta-feedback-tracking.md`:**

   ```markdown
   # Трекинг обратной связи беты

   ## Источники

   - Feedback-кнопка (10.2) → служебный канал
   - Чат беты (живые сообщения)
   - Еженедельные feedback-сессии (структурированно)
   - Sentry (технические проблемы)

   ## Где фиксируем

   - Лёгкий трекер: GitHub Issues (метки) ИЛИ простая таблица (Notion/Google Sheets)
   - Для соло-MVP: GitHub Issues с метками удобно (рядом с кодом)

   ## Категоризация

   - **bug** — что-то сломано
   - **ux** — неудобно, но работает
   - **feature-request** — хотят новое
   - **question** — непонятно (→ FAQ кандидат)

   ## Приоритизация

   - Частота: сколько организаторов упомянули (1 vs все)
   - Влияние: блокирует ценность или косметика
   - Усилие: быстрый фикс vs большая работа
   - → матрица частота×влияние определяет порядок

   ## Процесс

   1. Поступило → зафиксировать (issue/строка) с источником, категорией
   2. Триаж: severity (из support-runbook), частота
   3. Решение: фиксим сейчас / backlog / отклоняем (с объяснением)
   4. Если question, повторяющийся → добавить в FAQ (10.4)
   5. Закрытие → подтвердить организатору (если он репортил)

   ## Связь с разработкой

   - bug P0/P1 → hotfix
   - feature-request → оценить для post-beta (Phase 11+)
   - паттерны (много похожих) → сигнал для product-решений

   ## Гейт-связь

   - ≤5 критических жалоб (гейт-критерий) — считаем P0/P1 bugs
   - Повторяющиеся feature-requests → вход для Phase 11+ roadmap
   ```

2. **Выбрать инструмент** — GitHub Issues (рядом с кодом, метки) рекомендуется для соло. Таблица — если предпочитаешь.

3. **Связь с FAQ (10.4)** — повторяющиеся вопросы → дополнять FAQ (снижает будущую поддержку).

4. **Связь с гейтом (10.6)** — критические жалобы считаются для гейт-критерия «≤5».

## Критерии приёмки

- ✅ Runbook beta-feedback-tracking.md
- ✅ Источники, где фиксируем, категоризация, приоритизация
- ✅ Процесс (поступило → триаж → решение → закрытие)
- ✅ Инструмент выбран (GitHub Issues / таблица)
- ✅ Связь с FAQ (повторяющиеся вопросы)
- ✅ Связь с гейтом (критические жалобы)
- ✅ Лёгкий процесс (соло-MVP)

## Подсказки

- **GitHub Issues для соло** — метки (bug/ux/feature/question), milestone для post-beta, рядом с кодом. Не нужен отдельный трекер.
- **Частота × влияние** — главный приоритизатор. Один человек попросил фичу vs все жалуются на баг — разный приоритет.
- **Повторяющиеся вопросы → FAQ** — закрывает будущую поддержку. Цикл улучшения.
- **Не терять** — главная цель. Любой канал → зафиксировано. Иначе теряется в чате.

## Не делать

- ❌ Не внедрять Jira/тяжёлый процесс (соло-MVP)
- ❌ Не терять обратную связь в чате (фиксировать)
- ❌ Не игнорировать паттерны (повторяющееся = сигнал)

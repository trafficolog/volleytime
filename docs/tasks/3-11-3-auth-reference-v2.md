# Task 3.11.3: Авторизация и все состояния v2

## Цель

Привести веб-вход и состояния входа Mini App к `6 Авторизация.html`, не ослабляя текущую проверку личности.

## Контекст

Референс показывает 7 Web-состояний и 4 Mini App-состояния, перечисленные в [карте v2](../design/2026-09-23-reference-v2.md); текущая страница входа визуализирует только email/OTP и общий error.

Решение пользователя: веб-вход только по email-коду, Telegram-кнопка ведёт к рабочему боту с кнопкой Mini App; выбор организации, отказ в доступе и приостановку строим сейчас на реальном API, а итоговый desktop-маршрут подключаем в 5.15.1. Подробные переходы и границы приведены в [спецификации](../superpowers/specs/2026-09-24-auth-mvp-v2-design.md).

## Что должно быть сделано

1. Реализовать 7 достижимых Web-состояний из реального auth/org state: выбор способа, OTP, неверный код, loading, выбор org, нет прав организатора, приостановленная org.
2. Отобразить splash, неверный initData, отсутствие групп, закрытый доступ в Mini App с понятным следующим шагом.
3. Сохранить Telegram signed initData и существующий email OTP; ссылки и причины отказа должны быть действующими, а не прототипными.
4. TDD для переходов, ошибок и границ доступа; проверить клавиатуру, объявление ошибок и responsive.

## Критерии приёмки

- Все 11 состояний проверены, включая неправильный/просроченный код, несколько org и заблокированную org.
- Веб-игрок без прав организатора не получает desktop-кабинет; Mini App не подменяет signed identity.
- Пять gates зелёные, smoke auth проходит.

## Подсказки

## Дефект финального review 2026-09-27

- `useAuth().fetchSession()` скрывает ошибку `/api/auth/get-session` и подменяет её `user = null`. На `/m/` это делает сетевой/серверный сбой неотличимым от действительного отсутствия сессии: браузер отправляется на email-вход вместо состояния «Повторить проверку». После успешного Telegram sign-in тот же сбой не должен продолжать навигацию без подтверждённой клиентской сессии. До merge сохранить различие: успешный ответ без пользователя означает отсутствие входа, отклонённый запрос означает повторяемую ошибку; существующий пользователь не должен теряться при временном сбое. RED → GREEN на настоящем `useAuth` и переходе `enterMiniApp`, затем пять gates и локальный smoke.
- RED: два теста на настоящем `useAuth` упали: `fetchSession()` разрешался вместо отклонения, а `enterMiniApp()` отправлял браузер на email-вход вместо `browser_error`. GREEN: `fetchSession()` сохраняет прежнего пользователя и передаёт ошибку вызывающему коду; успешный ответ `user: null` по-прежнему очищает состояние. Целевые тесты `useAuth`, `mini-auth-state` и `auth-flow` — 17/17.
- Полные gates после исправления: `pnpm format:check` — pass; `pnpm lint` — 0 ошибок / 21 существующее предупреждение; `pnpm typecheck` — 6/6; `pnpm test` — 87 файлов / 479 тестов; `pnpm build` — 2/2. Повторный локальный smoke на изолированной БД: health, session, подписанный тестовый `initData`, список организаций, отказ подделки и cleanup — pass; webhook без Caddy/бота не проверялся.
- Browser QA собранного приложения: принудительный HTTP 503 для `/api/auth/get-session` оставил `/m/` на ошибке «Не удалось проверить вход. Попробуйте ещё раз» с кнопкой повтора. После снятия принудительного отказа повтор отправил действительно анонимного пользователя на `/auth/login?redirect=/m/`. Два сообщения консоли соответствовали только ожидаемым HTTP 503.

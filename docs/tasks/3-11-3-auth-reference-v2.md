# Task 3.11.3: Авторизация и все состояния v2

## Цель

Привести веб-вход и состояния входа Mini App к `6 Авторизация.html`, не ослабляя текущую проверку личности.

## Контекст

Референс показывает 7 Web-состояний и 4 Mini App-состояния, перечисленные в [карте v2](../design/2026-09-23-reference-v2.md); текущая страница входа визуализирует только email/OTP и общий error.

Решение пользователя: веб-вход только по email-коду, Telegram-кнопка ведёт к рабочему боту с кнопкой Mini App; выбор организации, отказ в доступе и приостановку строим сейчас на реальном API, а итоговый desktop-маршрут подключаем в 5.15.1. Подробные переходы и границы приведены в [спецификации](../superpowers/specs/2026-09-24-auth-mvp-v2-design.md).

## Что должно быть сделано

1. Реализовать 7 достижимых Web-состояний из реального auth/org state: выбор способа, OTP, неверный код, loading, выбор org, нет прав организатора, приостановленная org.
2. Отобразить splash, неверный initData, отсутствие групп, закрытый доступ в Mini App с понятным следующим шагом.
3. Сохранить Telegram signed initData и существующий email OTP; ссылки и причины отказа должны быть действующими, а не прототипными.
4. TDD для переходов, ошибок и границ доступа; проверить клавиатуру, объявление ошибок и responsive.

## Критерии приёмки

- Все 11 состояний проверены, включая неправильный/просроченный код, несколько org и заблокированную org.
- Веб-игрок без прав организатора не получает desktop-кабинет; Mini App не подменяет signed identity.
- Пять gates зелёные, smoke auth проходит.

## Подсказки

- Не считать mock-организации и mock-учётные записи из JSX реальными данными.

## Дополнение QA 2026-09-27

- Использовались отдельный PostgreSQL 16 на `127.0.0.1:55433`, веб на `127.0.0.1:3141`, только синтетические аккаунты/организации и консольный email-драйвер. Семь Web-состояний пройдены в браузере: начальная форма, ввод OTP, неверный и искусственно просроченный код с `role=alert`, `role=status` и `aria-busy` во время задержанного запроса, выбор двух организаций, отсутствие прав организатора у действующего игрока, приостановленная организация. Дополнительно проверены отдельная ошибка загрузки списка и восстановление без повторного OTP, смена аккаунта с выходом из сессии, открытие активной организации.
- Четыре Mini App-состояния проверены локально: splash со статусом, отвергнутый сервером тестовый `initData` (HTTP 401, retry снова вызвал endpoint), пустой список групп действующей сессии с действиями приглашения/создания, прямой вход в чужую группу с HTTP 403 и без раскрытия её названия. Прямой вход в приостановленную группу также показал отдельную причину без имени в заголовке. Обычный браузер без Telegram-сессии перешёл с `/m/` на `/auth/login?redirect=/m/`.
- Auth smoke на этой же тестовой БД: health, session endpoint, подписанный синтетический Telegram-вход, авторизованный список организаций, отказ поддельного `initData` и удаление smoke-аккаунта прошли. Это не является проверкой настоящего Telegram-host или BotFather.
- Browser RED → GREEN для адаптивности: до исправления при viewport 320 px и двух организациях ширина документа была 351 px, содержимого кнопки 312 px при ширине кнопки 243 px. После исправления с ещё более длинным реальным именем организации ширина документа и viewport совпали (320 px), кнопка и её содержимое заняли 243 px, высота кнопки 116 px. На desktop 1440 px горизонтального переполнения нет. Keyboard Tab достигает обеих организаций, фокус имеет видимый outline 2 px, Enter открывает выбранное состояние. Скриншоты сохранены только в локальных артефактах browser QA.
- После обоих локальных исправлений пять gates повторно прошли: `pnpm format:check`; `pnpm lint` (0 ошибок, 21 предупреждение вне изменённых файлов); `pnpm typecheck` (6/6); `pnpm test` (87 файлов, 474 теста, интеграционные тесты на изолированной PostgreSQL); `pnpm build` (2/2). Auth smoke повторно прошёл с синтетическим Telegram ID и очистил тестовый аккаунт. GitHub CI PR #41 на прежнем head `f243b89` имел зелёные lint/format/typecheck, tests и build; после публикации нового head потребуется свежий CI run.
- Первый `pnpm format:check` после browser QA нашёл 63 сгенерированных YAML-снимка в незатреканной `.playwright-cli/`, включая существовавшие до этого прогона файлы. Это не исходный код; чтобы требуемый gate проверял проект, а QA-артефакты оставались нетронутыми, директория добавлена в `.prettierignore`. Повторный gate прошёл.
- Дополнительный дефект QA: экраны HTTP 403 для чужой или приостановленной группы показывали нижнюю навигацию «Главная / События / Записи» с URL той же недоступной группы. Причина — layout `miniapp-org` строил player tabs при ошибке загрузки организации. Browser RED зафиксировал табы на экране 403. После исправления denial и suspended показывают только безопасное действие «К доступным группам», а после успешной загрузки организации табы остаются (локальная browser-проверка с подставленными API-ответами). Реальный HTTP 403 чужой группы на тестовой PostgreSQL проверен до этой локальной правки.

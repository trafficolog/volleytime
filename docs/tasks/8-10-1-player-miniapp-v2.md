## QA-дефект отменённой записи, 2026-09-24

- Локальная собранная версия после клика «Отменить запись» фактически перевела тестовую бронь в `cancelled` (БД и занятость `0/12`). Однако Home оставил её в «Моих ближайших записях» и показал «Записан». `listMyBookings(upcoming)` по контракту истории фильтрует только дату; dashboard не исключает отменённые записи до `limit`. В dashboard нужны только действующие будущие записи без ложной подписи и с корректным заполнением лимита даже после нескольких отмен.
- Детали этого события показывают повторную запись, но не статус отмены: `eventService.statsFor` скрывает `cancelled` в `myBooking`. Для 8.10.1 требуется одновременно явно показать «Запись отменена» и сохранить доступную повторную запись. Read-model `myBooking` должен передавать отменённую запись; занятость/лист ожидания и серверные правила бронирования не меняются. Списки событий не должны выдавать отменённую бронь за действующую.
- Исправление выполняется по RED → GREEN на сервисном read-model и UI-проекциях; повторить браузерный smoke на реальной отменённой записи. Не менять default-семантику `/bookings/my` и не трогать production.

## QA-дефект прямой ссылки на событие, 2026-09-25

- На локальной QA-группе Home показывает информационные состояния `pending` («Заявка на рассмотрении») и `suspended` («Группа приостановлена»), но прямой маршрут `/m/orgs/{orgId}/events/{eventId}` в обоих состояниях выводит только «Не удалось открыть событие» с бесполезным «Повторить». API события закономерно возвращает 403 (`forbidden.pending_approval` или `organization.suspended`); расширять права чтения нельзя.
- Причина — event detail отдаёт приоритет общей ошибке над уже вычисленным доступом, а код tenant-ошибки организации не передаёт в `playerHomeAccess`. До приёмки показать на прямой ссылке понятное информационное состояние и выход «Мои группы» без действия записи/Telegram MainButton. Настоящая сетевая ошибка остаётся ошибкой с повтором; загрузка не должна мигать ложным информационным состоянием. RED → GREEN тестировать приоритет состояния и подтвердить в браузере на `pending` и `suspended` фикстурах.
- Дополнительная проверка `blocked`: tenant middleware возвращает `permission.blocked` до DTO группы, поэтому Home, Profile и event detail вместо предусмотренного `denied` показывают общую ошибку с бесполезным повтором. В тех же MVP-маршрутах отобразить информационное «Доступ в группу закрыт» с переходом к «Моим группам», не расширяя API-доступ. Коды `permission.not_member` и `permission.no_longer_member` относятся к тому же закрытому доступу; иные/сетевые ошибки сохраняют Retry. Подтвердить RED → GREEN проекций и browser smoke `blocked`, затем вернуть QA-участника в `active`.
- До приёмки исправить прямые `events`, `bookings`, `subscriptions` при `pending`/`blocked`: локальный браузерный проход для `pending` видит API-ошибку с Retry, хотя изменение статуса участника требует действия организатора, а не повтора игрока; эти страницы обрабатывают другие tenant-ошибки тем же способом. Использовать известный API-код для информационного состояния с выходом «Мои группы» только при `pending`, `suspended`, `denied`; реальные сетевые ошибки сохраняют Retry. Для `Profile` дополнительно проверить `suspended`. RED → GREEN для классификации ошибок, browser smoke прямых маршрутов и восстановление QA-фикстур обязательны; API-права не расширять.

Согласовать команду в QA-документации и проверить оба варианта без изменения проверочных условий.
- GREEN: оба production-preview origin `http://localhost:3100` и `http://localhost:3142` проверены отдельными `open/goto` перед `run-code`: `player-miniapp-fidelity.pwcode` — 41/41 на каждом; group-race и network-retry — exit 0 на каждом; real-screen-matrix — 28/28 на каждом с новым локальным email-OTP входом игрока и настоящими QA API. Скрипты не содержат больше порта `3142`; фикстуры и критерии измерения не изменены. Локальные preview и браузер закрыты, реальный Telegram/WebView QA остаётся открытым.

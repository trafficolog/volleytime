# Оркестрация агентов

> Как задачи референса v3 (фазы 19–26) реализуются агентами: кто берёт задачу, какой моделью, кто проверяет и как работа попадает в `main` и `prod`.
> Последовательность работы над одной задачей — [DEVELOPMENT_PROCESS](./DEVELOPMENT_PROCESS.md); инженерные правила и gates — [CODING_STANDARDS](../CODING_STANDARDS.md); состав релизов — [RELEASES](./RELEASES.md); порядок фаз и волны — [ROADMAP](./ROADMAP.md#референс-v3-фазы-1926). Этот документ их не дублирует.

## Роли

| Роль          | Кто                                         | Отвечает за                                                                                                                                       |
| ------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Оркестратор   | основная сессия, `claude-opus-5-5`          | выбор готовых задач, запуск агентов, проверка evidence, merge после review/CI, синхронизация карточек и статуса                                   |
| Исполнитель   | агент `vt-implementer`, модель `impl_model` | реализация одной карточки в своей ветке и worktree: TDD, gates, визуальная сверка, PR                                                             |
| Ревьюер       | агент `vt-reviewer`, модель `review_model`  | независимое ревью diff против карточки и стандартов; не тот же агент, что реализовал                                                              |
| Визуальная QA | агент `vt-visual-qa`, `claude-sonnet-5-5`   | отчёт сверки с референсом через харнесс [19.0.2](./tasks/19-0-2-visual-reference-harness.md)                                                      |
| Владелец      | человек                                     | решения [D-xx](./operations/decisions/2026-10-12-reference-v3-decisions.md), Telegram QA на устройствах, настройки GitHub, подтверждение выкладки |

Агенты определены в [`.claude/agents/`](../.claude/agents/). Модель исполнителя и ревьюера берётся из карточки и передаётся параметром `model` при запуске агента; значение по умолчанию в определении агента — запасное.

## Маршрутизация моделей

Поля карточки: `complexity`, `impl_model`, `review_model`, `review_gate`. Значения заданы при перепланировании 19.0.1 по правилам референса и переопределены там, где задача касается денег или доступа.

| Сложность | Что это                                                                 | Реализация          | Ревью по умолчанию        |
| --------- | ----------------------------------------------------------------------- | ------------------- | ------------------------- |
| S         | вёрстка по готовому макету, тексты, переименования                      | `claude-haiku-5-5`  | `claude-sonnet-5-5`       |
| M         | компоненты с состоянием, формы, CRUD, известный API                     | `claude-sonnet-5-5` | `claude-sonnet-5-5`       |
| L         | несколько экранов и сущностей, новые эндпоинты                          | `claude-sonnet-5-5` | `claude-opus-5-5`         |
| XL        | архитектура, деньги, фоновые задачи, алгоритмы, доступ, LLM, SEO-рендер | `claude-opus-5-5`   | `claude-opus-5-5` + тесты |

Обязательные правила:

1. Деньги и баланс (цена, сборы, касса, возвраты, списания, выплаты) — ревью `claude-opus-5-5`, тесты граничных случаев и гонок.
2. Доступ (initData, роли, приглашения, root) — ревью `claude-opus-5-5`, IDOR-тесты на каждый новый эндпоинт.
3. Если задача меняет модель данных, схему и контракт сначала задаёт `claude-opus-5-5` (ADR [19.2.1](./tasks/19-2-1-domain-model.md) или отдельный шаг в карточке), затем UI — `claude-sonnet-5-5`.
4. `claude-haiku-5-5` не трогает бизнес-логику, API и схему. Если в задаче они понадобились — исполнитель останавливается и возвращает задачу оркестратору для переназначения.
5. `review_gate: owner` — решение принимает владелец; агент только готовит материалы.

Сводка по пулу v3: 88 задач; реализация — Opus 20, Sonnet 60, Haiku 8; ревью — Opus 55 (из них 16 с обязательными тестами граничных случаев), Sonnet 33. Точные значения — в карточках.

## Готовность задачи

Оркестратор запускает исполнителя только когда:

- все `depends_on` в статусе `done` (или `superseded`);
- все `decisions` в [журнале решений](./operations/decisions/2026-10-12-reference-v3-decisions.md) имеют решение;
- нет другой задачи в работе, которая меняет те же файлы схемы или миграций (см. «Параллельность»).

## Жизненный цикл задачи

1. **Захват.** Оркестратор ставит карточке `status: in_progress`, создаёт ветку `trafficolog/<type>/<id>-<slug>` от свежего `main` и отдельный worktree.
2. **Запуск исполнителя** с промптом по шаблону ниже и `model = impl_model`.
3. **Исполнитель:** читает карточку целиком, CODING_STANDARDS и DEVELOPMENT_PROCESS; для XL сначала пишет план шагов в PR-описание; TDD RED→GREEN; пять gates; для UI — отчёт сверки 19.0.2; коммиты с трейлерами `Task:` и `Release:`; открывает PR в `main`.
4. **Ревью.** Оркестратор запускает `vt-reviewer` с `model = review_model` в чистом контексте: карточка, diff PR, evidence. Находки уровня Critical/Important возвращаются исполнителю.
5. **Цикл исправлений** — до трёх раундов. Дальше оркестратор эскалирует: переназначает на `claude-opus-5-5` или выносит вопрос владельцу.
6. **CI** на exact head PR зелёный (обязательные проверки `main`, в том числе для администраторов, см. [GITHUB_SETUP](./GITHUB_SETUP.md#8-cicd-и-защита-веток)).
7. **Merge** оркестратором, затем синхронизация карточки: `status: done`, `last_reviewed`, ссылки на PR/CI в `status_note`.
8. **Релиз** — отдельная задача эпика «Релиз vX» (20.7.1, 21.3.1 …): сквозная QA, Promote, backup, smoke, тег. Merge задачи не означает выкладку.

## Параллельность

- Задачи одной волны ([ROADMAP](./ROADMAP.md#волны-исполнения)) без взаимных зависимостей идут параллельно, каждая в своём worktree. Одновременно — не больше трёх исполнителей.
- **Миграции сериализуются.** Drizzle нумерует миграции последовательно: две ветки с новой миграцией конфликтуют. В работе одновременно только одна задача с изменением схемы; следующая перегенерирует миграцию после rebase на `main`.
- Фазы могут перекрываться: задача фазы 21 стартует, как только закрыты её `depends_on`, не дожидаясь релиза v0.2.0. Релизная задача собирает итог.
- Required checks `main` с `strict: false`: перед merge ветку не обязательно обновлять, но после каждого merge CI на `main` перепроверяет итоговый SHA; Promote принимает только SHA с зелёным main CI. При конфликте миграций ветку всё равно нужно обновить от `main`.

## Шаблон промпта исполнителя

```text
Ты реализуешь задачу <ID> проекта Volley Time в worktree <path>, ветка <branch>.
Прочитай целиком: docs/tasks/<file>.md, CODING_STANDARDS.md, docs/DEVELOPMENT_PROCESS.md, AGENTS.md.
Референс: файлы из поля reference карточки (docs/design/reference-v3/...).
Сделай только то, что в карточке; соблюдай «Не делать». TDD RED→GREEN.
Перед PR: pnpm format:check, pnpm lint, pnpm typecheck, pnpm test (с PostgreSQL), pnpm build.
UI: отчёт визуальной сверки (харнесс 19.0.2) приложи к PR.
Если нужна бизнес-логика вне карточки, решение владельца или модель выше твоей — остановись и верни вопрос.
Итог: ссылка на PR, результаты gates с SHA, отклонения от карточки.
```

## Шаблон промпта ревьюера

```text
Независимое ревью задачи <ID>, PR <url>, head <sha>.
Карточка: docs/tasks/<file>.md. Стандарты: CODING_STANDARDS.md.
Проверь: соответствие «Что должно быть сделано» и «Критериям приёмки», «Не делать», корректность
(деньги, доступ, конкурентность — особо), тесты, миграцию (forward-compatible), совпадение UI с reference.screens.
Ответ: список находок Critical / Important / Minor с файлом и строкой; вердикт merge / changes.
Не правь код сам.
```

## Evidence

- Результаты gates с tested SHA, ссылка на CI и вердикт ревью — в описании PR.
- Отчёт визуальной сверки — вложение PR; для релизных задач — `docs/operations/qa/<дата>-<релиз>.md`.
- Статус проекта — [current-state](./operations/status/current-state.md): короткая запись после каждого релиза, без копирования логов.

## Действия только владельца

- Решения D-xx и утверждение новых состояний макета.
- Настройки GitHub: защита веток (`scripts/github/apply-branch-protection.sh --apply`), required reviewers environment `production`, секреты.
- Подтверждение выкладки, если в environment `production` включены reviewers; Telegram QA на реальных устройствах; приёмка релиза.

Агент не выполняет эти действия без явного согласия владельца в чате.

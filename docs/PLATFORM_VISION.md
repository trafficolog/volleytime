# 🎯 Platform Vision

> **Last updated:** 2026-05-25
> **Status:** утверждённое видение
> **Контекст:** документ синтезирует стратегические решения, принятые после анализа двух предшественников (Python-прототип, Laravel Level Volley) и обсуждения SaaS-перспектив.

---

## TL;DR в одном абзаце

Volley Time — это **Telegram-first платформа для организаторов любительских спортивных событий**. Стартует как инструмент для одного клуба (volleyball, Минск), архитектурно построена как SaaS-ready модульный монолит. Монетизация — через **event credits** (организатор покупает право создавать события), не через комиссию с оплат игроков. После подтверждения продуктовой гипотезы на private beta из 2–5 организаторов — расширение модулями (online payments, contributions, reports, потом турниры, потом CRM).

---

## Что строим (формулировка)

> **Telegram-first платформа для организации любительских спортивных событий: тренировки, открытые игры, абонементы, сборы, waitlist, напоминания, отчёты и в будущем — турниры. Доступ — через Telegram Mini App (основной интерфейс) и веб-приложение (для админов и публичных страниц).**

## Что НЕ строим (антицели на ближайшие 12+ месяцев)

- Публичный SaaS-маркетплейс с самообслуживанием для тысяч клубов.
- Платёжного посредника между игроками и организаторами.
- Микросервисы.
- Полноценный web admin кабинет до проверки гипотезы.
- Сложный split-payments / marketplace billing.
- Мобильное native-приложение (iOS / Android).
- BI-платформу с аналитическими дашбордами.
- Маркетинговые рассылки и SMS-уведомления.

## Стратегическая модель развития

```
Этап 1 — Python-прототип (legacy)
  └── одна группа в Минске на пару месяцев
  └── живая проверка UX: запись, абонементы, ручная оплата
  └── domain knowledge переносится в новый стек

Этап 2 — Новая платформа: ядро MVP (Phase 3–8)
  └── Nuxt 4 + Drizzle + PG + better-auth + grammY
  └── Telegram Bot + Mini App как основной интерфейс
  └── Organizations + Members + Invites + Events + Bookings + Subscriptions + Manual Payments
  └── Event Credits как платформенная монетизация

Этап 3 — Production + Private Beta (Phase 9–10)
  └── Минимальный production deploy
  └── 2–5 организаторов на закрытом тесте
  └── Telegram Mini App у реальных игроков
  └── Проверка гипотезы:
      ├── Готовы ли организаторы платить за event credits?
      ├── Удобен ли Mini App для игроков?
      ├── Достаточно ли функций ядра без турниров и CRM?

═══════════ ГЕЙТ: подтверждение гипотезы ═══════════

Этап 4 — Расширение (Phase 11–15)
  └── Contributions (сборы)
  └── Online Payments (bePaid) — own org, потом organizer add-on
  └── Reports & Export
  └── Reminders & Automation (APScheduler-аналог)

═══════════ ГЕЙТ: запрос крупных клубов ═══════════

Этап 5 — Турнирный модуль (Phase 16–17)
  └── Порт Level Volley (Laravel → Nuxt)
  └── Matches + Live Scoreboard + Stats
  └── Tournament Mode (соединение Events и Matches под турнирные сетки)

═══════════ ГЕЙТ: запрос на полноценную CRM ═══════════

Этап 6 — CRM Pro (Phase 18)
  └── Заметки о игроках, теги, сегменты
  └── No-show аналитика
  └── Рассылки по сегментам
```

**Ключевой принцип:** между этапами есть гейты подтверждения гипотезы. Каждый этап — это **возможность остановиться**, если продукт не востребован, и не тратить ресурсы зря.

## Бизнес-модель

### Что продаёт платформа

Платформа продаёт **организатору** инструмент:

- создание событий с распределением слотов
- waitlist и автопродвижение
- абонементы
- учёт оплат (ручной или онлайн — на выбор организатора)
- сборы
- напоминания
- отчёты
- (в будущем) турниры, CRM

### Чего платформа НЕ делает на старте

Платформа **не принимает деньги** за организаторов. Игрок платит организатору напрямую:

- наличными
- переводом на карту
- через эквайринг организатора (если у него есть)
- через онлайн-модуль (когда он будет подключаемым add-on)

Это критично для юридической и налоговой простоты. См. [docs/guides/TAXES.md](./guides/TAXES.md).

### Монетизация: Event Credits

Основная ранняя модель — **event credits**: организатор покупает у платформы право создать N событий.

| Пакет       | Цена (пример) |
| ----------- | ------------- |
| 1 credit    | 5 BYN         |
| 10 credits  | 40 BYN        |
| 30 credits  | 90–120 BYN    |
| 100 credits | 250–350 BYN   |

**Правила списания:**

- Создание события → -1 credit
- Отмена до открытия записи → +1 credit (возврат)
- Отмена после записей → по правилам тарифа
- Тестовые события — из demo-квоты или без списания

**Преимущества модели:**

- Прозрачная, без процента с оборота
- Не требует marketplace-лицензий и сложных договоров
- Игроки не воспринимают платформу как финансового гаранта
- Лёгкая интернационализация (можно в любой валюте)

### Будущие модели (после private beta)

- **Месячные подписки** для активных организаторов (Regular, Club, Pro)
- **Add-ons** (Online Payments, CRM, Tournaments, Public Page)
- **Tournament-tier** для организаторов соревнований
- **Custom-тариф** для федераций и сетей залов

Подробности — в [docs/strategy/ORGANIZER_MONETIZATION.md](./strategy/ORGANIZER_MONETIZATION.md) и [docs/strategy/BILLING_AND_ENTITLEMENTS.md](./strategy/BILLING_AND_ENTITLEMENTS.md).

## Архитектурная философия

### Modulith, не микросервисы

Один deploy, одна PostgreSQL, чёткие границы между модулями через public service APIs. Подробно — в [docs/architecture/MODULITH_ARCHITECTURE.md](./architecture/MODULITH_ARCHITECTURE.md).

### Multi-tenancy с первого дня

`Organization` — root aggregate / tenant. **Все** операционные сущности (Event, Booking, Subscription, Payment, LedgerEntry, ContributionCampaign, Venue) имеют `organization_id`.

`User` — глобальная сущность. Один Telegram-аккаунт может быть участником нескольких организаций.

Связь User ↔ Organization — через `OrganizationMember` с ролями (owner / organizer / assistant / player) и статусом (active / pending / guest / blocked / left).

### Feature entitlements

Модули включаются для организации не по названию тарифа, а через явные `OrganizationFeature` записи (source: plan / addon / trial / admin_grant). Это даёт гибкость:

- включить CRM на trial для конкретной организации
- дать beta-доступ к турнирам
- временно отключить модуль при просрочке оплаты
- сделать admin grant для тестовой организации

## Граница ответственности

В UX, оферте и onboarding явно фиксируется:

> **Организатор самостоятельно принимает оплату от игроков и отвечает за расчёты, возвраты и налоговые обязательства. Платформа предоставляет инструмент записи, учёта, уведомлений, абонементов, сборов и отчётов.**

Это критично для двух вещей:

1. Игроки не считают платформу финансовым гарантом в случае спора с организатором.
2. У платформы упрощённая юридическая модель (нет marketplace-лицензий).

## Что переносим из Python-прототипа

Из существующих Phase 1+2 (Python/aiogram/SQLAlchemy) переносится **domain knowledge**, не код:

- Логика распределения слотов: main → rotation → waitlist
- Атомарное списание сессий абонемента (через WHERE-условие)
- FIFO выбор абонемента для списания (по `expires_at`)
- Касса (Ledger) как append-only журнал
- Цикл подтверждения платежа: pending → succeeded / failed
- Промоушн из waitlist при отмене
- Цикл посещаемости: confirmed → attended / no_show
- Refund при отмене тренировки админом

---

## Что переносим из Level Volley (Laravel)

Из существующего Laravel-проекта **в будущем** (Phase 16-17) переносятся:

### Domain

- Events (с типом training / open_game / tournament_match / custom)
- Teams (с цветами, капитанами, drag-and-drop генерацией)
- Matches и Sets
- Match Timeline (append-only с `is_reverted` — золотой паттерн)
- Standings с настраиваемой `tiebreak_order`
- `scoring_system`: standard (3/2/1/0) vs sum_points
- MVP voting
- Live Scoreboard (auto-refresh)
- Event Staff (judge, event_admin)
- Role hierarchy и role requests
- Notifications с типами и badge
- Audit log с фильтрацией

### UX-паттерны

- Inline-editing с AJAX и индикаторами сохранения (✓ ⏳ ✗)
- Drag-and-drop игроков между командами
- QR-код для публичной страницы
- Tабы на странице события (Обзор / Команды / Матчи / Статистика)
- Mobile-first для судейской сессии с крупными кнопками «+1»

### Auth-паттерн

- Passwordless email-code (10 минут TTL)
- Rate limit (1 код / 60 сек, 5 попыток на код)
- CSRF-защита
- → реализуется через **better-auth** в новом стеке

## Метрики успеха по этапам

### Этап 2 (MVP до Private Beta)

- 1 организатор активно использует Mini App
- 5+ игроков записались через Mini App за неделю
- 1 цикл оплат прошёл (cash через ledger)
- 0 критических багов после прохождения тестов

### Этап 3 (Private Beta)

- 2–5 организаторов используют платформу ≥1 месяц
- 50+ событий создано
- 200+ записей сделано
- 80% операций выполняются через Mini App без обращения в поддержку
- 1+ организатор готов платить за event credits

### Этап 4 (Расширение)

- 10+ организаторов
- 30%+ событий оплачиваются онлайн через bePaid
- 5+ организаторов используют сборы
- CSV-экспорт для НПД используется регулярно

### Этап 5 (Турниры)

- 1+ клуб провёл турнир через платформу
- Live scoreboard выводился на проектор
- Полный цикл: команды → расписание → матчи → standings

## Критический путь

Самый короткий путь к проверке продуктовой гипотезы:

```
Phase 3 (Foundation)
   ↓
Phase 4 (Organizations + Members + Invites)
   ↓
Phase 5 (Events + Bookings + Subscriptions)
   ↓
Phase 6 (Manual Payments + Ledger)
   ↓
Phase 7 (Event Credits)
   ↓
Phase 8 (Telegram Bot + Mini App)  ← MVP-релиз!
   ↓
Phase 9 (Production Deploy)
   ↓
Phase 10 (Private Beta)            ← ГЕЙТ
```

Параллельно: Python-прототип в одной группе для domain validation.

Оценка: **3-4 месяца** до Phase 10 при разработке одним человеком.

## Решения, которые ещё предстоит принять

Ниже — открытые вопросы, на которые сейчас нет ответа. Они не блокируют старт, но требуют решения по ходу:

1. **Хостинг продакшен:** российский VPS — решено. Конкретный провайдер (Selectel / Timeweb) — Phase 9.
2. **Имя бренда:** «Volley Time» (домен `volleytime.by`) — финальное для волейбольной ниши. При расширении на другие виды спорта — ребрендинг в «ВТЕМПЕ» (vtempe.by / vtempe.ru). Решение — после Phase 10.
3. **География на старте:** Беларусь (Минск) + Россия. Хостинг в РФ, бренд изначально позиционируется для русскоязычного рынка.
4. **Open source модель:** repo приватный до Phase 10, далее — решение по результатам.
5. **Команда:** соло на старте. Поиск второго разработчика — после Phase 10.
6. **Юридическая модель:** РБ или РФ? Зависит от того, где будет основной денежный поток. Решается до Phase 7 (Event Credits, первая монетизация). См. [docs/guides/TAXES.md](./guides/TAXES.md).

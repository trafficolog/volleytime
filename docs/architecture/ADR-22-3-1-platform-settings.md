# ADR 22.3.1 · Настройки платформы (R-05)

- **Статус:** принято решениями владельца 2026-11-20 ([D-20](../operations/decisions/2026-10-12-reference-v3-decisions.md#d-20)); шаг схемы и контракта по правилу 3 [ORCHESTRATION](../ORCHESTRATION.md) (`claude-opus-5-5`) до реализации карточки [22.3.1](../tasks/22-3-1-platform-settings.md).
- **Область:** таблица `platform_settings` и реестр ключей, колонка безлимита событий у организации, миграция `0042`, контракт `/api/platform/settings` и `/api/platform/organizations/{id}/event-balance/unlimited`, чтение настроек в web и боте, история в `audit_log`, экран «Настройки» Root Admin.
- **Не область (D-20):** bePaid, инвойсы и подключение эквайринга (D-07); слово «credits» (D-10, только «баланс событий»); «demo-квота 5» как отдельная сущность (D-12 — заменяется настройкой стартового баланса); 2FA, IP-allowlist, активные сессии команды, API-ключи, вкладка «Команда & роли»; редактирование feature flags (остаются в env); TTL предложения листа ожидания (`OFFER_TTL_MS` = 30 мин, D-03, не редактируется); «Макс. игроков в org», «Бронь до подтверждения», «Rate limit бота msg/сек» (исходящий темп Bot API) из макета — в коде их нет и они не вводятся.

## Контекст

Макет R-05 (`handoff/screens-admin-forms.jsx`, `AdminSettings`) — восемь вкладок с моковыми полями. В коде до 22.3.1 все параметры — константы или env:

| Параметр                       | Где сейчас                                                                                                                             | Поведение                                                                                                          |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Стартовый баланс новой группы  | `EVENT_BALANCE_DEMO_QUOTA = 5` (`packages/db/src/event-balance.ts`), `eventBalanceService.grantDemoQuota` в транзакции создания группы | запись журнала `demo_grant` +5, уникальна на группу; пилотные 48 (D-12) — разовый `pilot_grant` при 20.2.1         |
| Списание при публикации        | `eventBalanceService.spendOnPublish` (`packages/core/src/event-balance/service.ts`), выключатель `EVENT_BALANCE_ENFORCED`              | `spend` −1 под блокировкой проекции; нехватка — 409 `event_balance.insufficient`; серия — `planSeriesDates` (D-04) |
| «Макс. событий / день»         | **нет** — только в макете (`10`)                                                                                                       | лимита нет                                                                                                         |
| Rate limit бота                | `callbackRateLimited` в `apps/bot/src/handlers/callbacks.ts`                                                                           | 8 нажатий inline-кнопок за 10 с на пользователя, в памяти процесса бота                                            |
| Rate limit `/api/auth/*`       | `RateLimiter` в `apps/web/server/utils/rate-limit.ts`                                                                                  | не редактируется (безопасность входа), показывается только как «включено»                                          |
| TTL предложения листа ожидания | `OFFER_TTL_MS` в `packages/core/src/bookings/offers.ts`                                                                                | 30 мин, не редактируется                                                                                           |

Бот не имеет доступа к БД: зависимости — только `grammy` и Sentry, данные он получает через внутренний API web (`apps/bot/src/web-client.ts`, `/api/internal/bot/*`, заголовок `x-internal-secret`). Поэтому «бот читает ту же таблицу» реализуется как чтение того же источника через web.

## Решение

### Схема (миграция `0042_platform_settings`)

Одна миграция для обеих частей, обе expand-only.

`platform_settings` — одна строка на ключ, отсутствие строки = значение по умолчанию из кода:

| Колонка      | Тип                                                | Правило                                                                     |
| ------------ | -------------------------------------------------- | --------------------------------------------------------------------------- |
| `id`         | `serial` PK                                        | `entity_id` в `audit_log`                                                   |
| `key`        | `text NOT NULL UNIQUE`                             | CHECK `key ~ '^[a-z][a-zA-Z]*\.[a-z][a-zA-Z]*$'`; allowlist — реестр в коде |
| `value`      | `jsonb NOT NULL`                                   | валидируется реестром Zod при записи и при чтении                           |
| `version`    | `integer NOT NULL DEFAULT 1`, CHECK `version >= 1` | оптимистичная блокировка; первая запись ключа — `1`                         |
| `updated_by` | `integer` FK `users(id) ON DELETE SET NULL`        | root, сделавший последнее изменение                                         |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()`               |                                                                             |
| `created_at` | `timestamptz NOT NULL DEFAULT now()`               |                                                                             |

Сида нет: значения по умолчанию в реестре равны текущему поведению, поэтому сразу после миграции поведение не меняется.

`organizations.event_balance_unlimited_until timestamptz NULL` — безлимит событий для отдельной группы (пункт «Лимиты» (d)). Хранится **исключающая** граница: для выбранной root даты `D` (последний день безлимита) — `D + 1` 00:00 Europe/Minsk, в UTC `D 21:00Z` (Минск — UTC+3 без перехода на летнее время; вычисление через `Intl`/таймзону `Europe/Minsk`, не через константу смещения). Безлимит активен, если `event_balance_unlimited_until > now()`. `NULL` — безлимита нет. Отдельная таблица не нужна: у группы одно текущее окно, история — в `audit_log`; кто и почему — в аудите, а не в колонках.

### Реестр ключей (`packages/shared/src/platform/settings.ts`)

Один объект `PLATFORM_SETTINGS` — `key → { schema (Zod), default, appliesTo, section }`. Ключ вне реестра — 422 `platform_settings.unknown_key`. Неизвестные ключи в БД (после отката кода) при чтении игнорируются; значение, не проходящее схему, при чтении заменяется значением по умолчанию с предупреждением в лог и Sentry.

| Ключ                                | Тип и границы                                                                              | По умолчанию        | Применяется                                                                                                               | Раздел UI |
| ----------------------------------- | ------------------------------------------------------------------------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------- |
| `general.platformName`              | строка после `trim`, 1–60 символов, без управляющих символов и переводов строк             | `'Volley Time'`     | web: шапка Root Admin, `<title>` страниц `/root`                                                                          | Общие     |
| `general.supportContact`            | `null` или строка после `trim`, 1–120 символов, без управляющих символов и переводов строк | `null`              | web: строка «Вопросы по оплате — …» на странице баланса кабинета (W-12) и в Root Admin; при `null` строка не показывается | Общие     |
| `eventBalance.newOrganizationGrant` | целое 1–1000                                                                               | `5`                 | web/core: начисление при создании группы                                                                                  | Лимиты    |
| `events.maxPublishedPerDay`         | `null` или целое 1–50                                                                      | `null` (нет лимита) | web/core: публикация событий, серии                                                                                       | Лимиты    |
| `bot.callbackLimit`                 | целое 1–100                                                                                | `8`                 | бот: нажатия inline-кнопок на пользователя                                                                                | Лимиты    |
| `bot.callbackWindowSeconds`         | целое 1–300                                                                                | `10`                | бот: окно этого лимита                                                                                                    | Лимиты    |

Схемы — `.strict()` для объектов, `z.number().int()` для целых (строка `"5"` — 422), строки отвергают `[\x00-\x1f\x7f]`. Добавление ключа — правка реестра и ADR, без миграции.

Семантика лимитов:

- **`eventBalance.newOrganizationGrant`.** `grantDemoQuota` начисляет значение настройки на момент создания группы, причина в журнале остаётся `demo_grant` (уникальный индекс «одно стартовое начисление на группу» сохраняется), комментарий — «Стартовый баланс новой группы: N событий». В интерфейсе — «Стартовый баланс новой группы (событий)», не «demo-квота» и не «credits». Минимум 1, а не 0: сверка 20.2.1 (`packages/db/src/event-balance-operations.ts`) считает группу без `demo_grant`/`pilot_grant` аномалией и доначисляет; нулевое начисление сломало бы этот инвариант. Сверка оператора по-прежнему доначисляет константу `EVENT_BALANCE_DEMO_QUOTA` (пакет `db` не зависит от `core`; это ремонт аномалий, а не создание группы). Пилотные 48 (D-12) — разовый `pilot_grant`, настройка его не повторяет и уже созданные группы не трогает. Создание группы root (22.1.8) берёт настройку как значение по умолчанию.
- **`events.maxPublishedPerDay`.** Лимита в коде нет, поэтому `null` = текущее поведение. Значение — сколько **опубликованных** неотменённых событий группы может начинаться в один календарный день Europe/Minsk (по `starts_at`). Проверка — там же, где списание: создание опубликованным, `draft → published`, перенос опубликованного события на другую дату (`PATCH` `startsAt`) — под той же блокировкой события, подсчёт в транзакции. Превышение — 409 `event.daily_limit_reached` с `{ date, limit }`; текст «В этот день уже N опубликованных событий — лимит платформы». Серия (`planSeriesDates`): дата сверх лимита становится черновиком с `draftReason = 'daily_limit'` по образцу D-04 и не списывает баланс. Черновики и отменённые не считаются. Безлимит группы на этот лимит не влияет.
- **`bot.callbackLimit` / `bot.callbackWindowSeconds`.** Заменяют константы 8 и 10 000 мс в `callbackRateLimited`. Исходящий темп Bot API (`rateLimitedUntil` в `packages/core/src/scheduler/journal.ts`, 429 от Telegram) не настраивается.

### Чтение и кэш

- Web/core: одна функция `getPlatformSettings(ctx)` в `packages/core/src/platform/settings.ts` возвращает полный типизированный объект (значение из БД или по умолчанию для каждого ключа). Кэш в памяти процесса, TTL 30 с; запись через сервис настроек сбрасывает кэш своего процесса **после коммита**. Ошибка чтения БД — значения по умолчанию, `console.warn` и Sentry без значений; ошибка не кэшируется дольше 5 с, чтобы не держать умолчания 30 с после кратковременного сбоя. Чтение внутри денежной транзакции (стартовое начисление, дневной лимит) берёт значение из кэша: устаревание до 30 с принято владельцем.
- Бот: новый внутренний маршрут `GET /api/internal/bot/settings` (тот же `x-internal-secret`, что у `/api/internal/bot/*`) отдаёт только ключи `bot.*`. Бот кэширует ответ 30 с в памяти; при ошибке запроса или невалидном ответе — значения по умолчанию (8 / 10 с), повтор через 30 с. Суммарная задержка применения в боте — до ~60 с (кэш web + кэш бота); в UI под разделом «Лимиты» подпись «Применяется в течение минуты».
- Процессов web несколько не бывает (один контейнер), поэтому межпроцессной инвалидации нет; при масштабировании задержка ограничена TTL.

### Безлимит событий группы

- **Проверка в момент использования, без фонового задания.** `spendOnPublish` после `lockEventBalance` читает `event_balance_unlimited_until` группы в той же транзакции (`SELECT … FROM organizations WHERE id = $1`); если `> now()` — списания нет, функция возвращает `null`, уведомление «Мало событий» не пишется. По истечении срока следующая публикация списывает как обычно.
- **Списания нет, маркера в журнале нет.** Выбран вариант «ничего не записывать» в `event_balance_entries`: CHECK `event_balance_entries_delta_non_zero` запрещает записи с нулём, проекция `organization_event_balances.balance` = сумма журнала остаётся верной без исключений, а сверка 20.2.1 не меняется. Отмена такого события не возвращает баланс: `refundOnCancel` требует существующего `spend`, поэтому повторного начисления «за бесплатное» событие не бывает. Какие события опубликованы без списания, восстанавливается из аудита окна безлимита и отсутствия `spend` по событию; отдельный отчёт не вводится.
- **Черновик, созданный в безлимит и опубликованный после**, списывает при публикации — значение проверяется в момент публикации. Событие, опубликованное в безлимит, после окончания срока не списывается задним числом.
- **Серии:** `previewSeries` и создание серии считают `enforced && !unlimited`; при активном безлимите все даты публикуются (кроме конфликтов площадки и дневного лимита), `balanceAfter` = текущий баланс. Создание пересчитывает план в транзакции, поэтому истечение между предпросмотром и созданием даёт черновики по D-04.
- **Бот** события не создаёт и баланс не проверяет (публикация идёт через web/core), отдельной проверки в боте нет.
- **`EVENT_BALANCE_ENFORCED = false`:** списания нет и так, безлимит ни на что не влияет.
- **Покупки и начисления** работают как обычно: заявки подтверждаются, `grant`/`purchase` увеличивают баланс, он сохраняется на время после безлимита. Безлимит не меняет баланс ни при установке, ни при окончании.
- **Кабинет и Mini App организатора:** `GET` баланса группы возвращает `unlimited: { until: 'YYYY-MM-DD' } | null` (последний день безлимита по Минску). Пока активен: на странице баланса (W-12) и в бейдже баланса — «Безлимит событий до 31.12.2026», рядом остаток «на балансе N событий — сохранится после»; предупреждения «Мало событий» и блокировки публикации по балансу скрыты; покупка пакетов доступна. За 3 дня до окончания — подпись «Безлимит заканчивается 31.12.2026».
- **Root Admin:** в карточке организации (22.1.3) блок «Безлимит событий»: «Включить до…» (дата, причина), «Продлить/изменить дату», «Отключить» (причина); в списке организаций — фишка «Безлимит до …».

API (root-only, конвенция `requireRoot`):

- `PUT /api/platform/organizations/{id}/event-balance/unlimited` `{ until: 'YYYY-MM-DD', reason }` → 200 `{ until, active: true }`. `until` — не раньше сегодняшней даты Минска и не позже сегодня + 366 дней; `reason` — строка 3–500 символов после `trim`, без управляющих символов. Удалённая (мягко) группа — 409 `organization.deleted`; нет группы — 404. Блокировка строки организации `FOR UPDATE`. Повтор с той же датой — 200 без новой записи аудита.
- `DELETE /api/platform/organizations/{id}/event-balance/unlimited` `{ reason }` → 200 `{ until: null }`; ставит `NULL`. Без активного безлимита — 200 без аудита.

### Запись настроек

- `GET /api/platform/settings` → 200, `Cache-Control: no-store`:

  ```json
  {
    "settings": {
      "general.platformName": {
        "value": "Volley Time",
        "default": "Volley Time",
        "version": 0,
        "updatedAt": null,
        "updatedBy": null
      }
    },
    "readonly": {
      "payments": {
        "currency": "BYN",
        "model": "manual_requests",
        "onlinePayments": false,
        "bankDetails": null
      },
      "general": { "region": "Europe/Minsk" },
      "security": { "authRateLimit": true, "rootAuditLog": true, "trustedProxy": true },
      "integrations": {
        "telegramBot": true,
        "telegramLoginWidget": true,
        "smtp": true,
        "sentry": true,
        "scheduler": true
      },
      "featureFlags": [{ "name": "EVENT_BALANCE_ENFORCED", "enabled": true }]
    },
    "applyDelaySeconds": 30
  }
  ```

  `version: 0` — строки нет (значение по умолчанию). `updatedBy` — `{ id, name }` или `null`. В `readonly` — только булевы статусы и неконфиденциальные константы; ключи, токены, адреса вебхуков, строки подключения и секреты не попадают в ответ **по построению**: обработчик собирает объект из allowlist выражений вида `Boolean(process.env.X)`, а не из перебора env. Feature flags — allowlist имён (`EVENT_BALANCE_ENFORCED`, `COLLECTIONS_ENABLED`, `EVENT_INVITE_MODE_ENABLED`, `EVENT_MULTI_SEAT_ENABLED`, `EVENT_SPLIT_PRICING_ENABLED`, `SCHEDULER_ENABLED`, `TELEGRAM_LOGIN_WIDGET_ENABLED`) со значением по правилу каждого флага.

- `PATCH /api/platform/settings` `{ changes: [{ key, value, version }] }` (1–20 элементов, ключи без повторов, `.strict()`) → 200 в форме `GET`. В одной транзакции: `SELECT … FOR UPDATE` строк по ключам; `version` должна совпасть с текущей (`0` — строки нет); иначе 409 `platform_settings.stale` с текущим `settings` — ни одно изменение не применяется. Вставка при `version = 0` — `INSERT … ON CONFLICT (key) DO NOTHING`, конфликт — тоже 409 stale. Значение, равное текущему действующему (сохранённому или по умолчанию, сравнение канонического JSON), — no-op: строка, `version` и аудит не меняются. Иначе `value` записывается, `version + 1`, `updated_by`, `updated_at`. Возврат к значению по умолчанию — обычная запись (строка остаётся, история цела); отдельного «сбросить» нет.
- Ошибки: 401 без сессии; 403 `forbidden.root_only` (проверка `assertRootAdmin` в core и `requireRoot` в маршруте); 422 `validation` с путём ключа при нарушении схемы; 422 `platform_settings.unknown_key`; 409 `platform_settings.stale`. Мутации — с проверкой Origin/CSRF, как в 22.1.x.

### История (`audit_log`)

В той же транзакции, актор — root (`user_id`), `organization_id = NULL` для настроек:

| Событие                 | `action`                            | `entity_type`      | `entity_id`            | `old_value` / `new_value`                                              |
| ----------------------- | ----------------------------------- | ------------------ | ---------------------- | ---------------------------------------------------------------------- |
| Изменён ключ настроек   | `platform_setting.updated`          | `platform_setting` | `platform_settings.id` | `{ key, value }` (старое — действующее, включая значение по умолчанию) |
| Безлимит включён        | `event_balance.unlimited_set`       | `organization`     | `organizations.id`     | `null` / `{ until, reason }`; `organization_id` = группа               |
| Дата безлимита изменена | `event_balance.unlimited_changed`   | `organization`     | `organizations.id`     | `{ until }` / `{ until, reason }`                                      |
| Безлимит отключён       | `event_balance.unlimited_cancelled` | `organization`     | `organizations.id`     | `{ until }` / `{ until: null, reason }`                                |

Одна запись на изменённый ключ; no-op не пишется. Истечение срока аудита не пишет (это не действие). Журнал R-07 (22.1.2) показывает новые действия с русскими подписями; страница настроек показывает историю последних изменений из того же журнала (`entity_type = 'platform_setting'`).

### Безопасность

- Секретов в таблице нет по построению: реестр не содержит ключей для токенов, паролей и URL с учётными данными; всё секретное остаётся в env и отдаётся только булевым статусом.
- Свободный текст (`platformName`, `supportContact`, `reason`) ограничен по длине, без управляющих символов, выводится только интерполяцией Vue (без `v-html`), в `<title>` — как текст; ссылкой `supportContact` не становится (никаких автоссылок на произвольный URL).
- Внутренний маршрут бота отдаёт только `bot.*`, проверяет секрет сравнением постоянного времени, как остальные `/api/internal/bot/*`.

### Экран «Настройки» (`/root/settings`)

Левое меню разделов (на мобильном 375 — горизонтальные чипы): **Общие**, **Платежи**, **Уведомления**, **Лимиты**, **Безопасность**, **Интеграции**. «Команда & роли», «Feature flags» как вкладка с переключателями, «API & вебхуки» не переносятся; флаги показываются блоком только для чтения в «Интеграции» с подписью «Меняются в конфигурации сервера».

- **Общие** — редактируемые «Название платформы», «Контакт поддержки»; только чтение «Валюта» (BYN), «Регион / часовой пояс» (Беларусь · Europe/Minsk). Кнопка «Сохранить» активна при изменениях.
- **Платежи** — только чтение: модель «Заявки организаций, ручное подтверждение» (D-07), онлайн-оплата «Не подключена», валюта, реквизиты «Не заданы». Без кнопки «Подключить bePaid» и без инвойсов.
- **Уведомления** — заглушка «Скоро» без переключателей.
- **Лимиты** — четыре поля: «Стартовый баланс новой группы (событий)», «Макс. опубликованных событий в день на группу» (пусто = без лимита), «Нажатия кнопок бота на пользователя» и «за секунд»; подпись «Применяется в течение минуты»; ниже — «Безлимит событий для отдельной группы настраивается в карточке организации».
- **Безопасность**, **Интеграции** — списки статусов «включено / не настроено» из `readonly`.
- Сохранение отправляет только изменённые ключи раздела с их `version`; 409 stale — сообщение «Настройки изменил другой администратор — данные обновлены», форма перезагружается; 422 — ошибка у поля. Под формой — последние изменения (кто, когда, ключ, было → стало).
- Визуальная сверка — вручную на 1440×900 и 375×812 (D-16), отчёт в PR.

### Миграция и откат

- `0042` — expand-only: `CREATE TABLE platform_settings`, `ALTER TABLE organizations ADD COLUMN event_balance_unlimited_until timestamptz NULL`. Без бэкфилла и сида, без preflight (новая таблица пуста, колонка `NULL` у всех строк). Снимок drizzle обновляется.
- **Откат приложения на предыдущий релиз разрешён без флага, capability label и расширения rollback guard.** Старый код не читает таблицу и колонку (Drizzle с явными списками колонок; INSERT группы оставляет колонку `NULL`). Ограничения, которые фиксируются в runbook: после отката действуют значения по умолчанию из кода (стартовый баланс 5, без дневного лимита, 8 нажатий за 10 с), а группы с активным безлимитом снова списывают баланс при публикации и упираются в него. Перед откатом оператор смотрит `SELECT id, name, event_balance_unlimited_until FROM organizations WHERE event_balance_unlimited_until > now();` и сообщает владельцу; при необходимости root начисляет баланс вручную (22.2.2).
- `packages/db/rollback/0042_platform_settings.sql` по образцу 0040: отказывает (`RAISE EXCEPTION`), если `EXISTS (SELECT 1 FROM platform_settings)` или `EXISTS (SELECT 1 FROM organizations WHERE event_balance_unlimited_until IS NOT NULL)` — значения введены root вручную, их история есть в аудите, но восстанавливать их руками — решение владельца. Иначе снимает колонку и таблицу. Обход — после `pg_dump -t platform_settings` и выборки колонки, затем `pnpm db:rollback` в одной транзакции.
- Реализация добавляет в [deploy runbook](../operations/runbooks/deploy.md) раздел «v0.4.0 platform settings: no flag, no guard extension (Task 22.3.1)» по образцу разделов 0040/0041 (включая read-only проверку `SELECT key, value, version FROM platform_settings ORDER BY key;`) и тесты: миграционный (старый путь INSERT организации на новой схеме), rollback (проходит на пустых данных, отказывает при строке настроек и при заданном безлимите), граничные значения реестра, stale 409, no-op без аудита, безлимит на границе Минска (последний день включительно, следующий день — списание), серия при безлимите и дневном лимите, внутренний маршрут бота без секрета — 401.

## Последствия

- `+` Root меняет стартовый баланс, дневной лимит и лимит бота без деплоя; история — в общем журнале.
- `+` Безлимит пилотных/демо групп без ручных начислений и без искажения журнала баланса; окончание срока не требует задания.
- `+` Секреты не попадают в БД и ответы API по построению; откат приложения свободен.
- `−` Изменение применяется с задержкой до ~30 с в web и ~60 с в боте.
- `−` После отката приложения группы с безлимитом снова списывают баланс.
- `−` События, опубликованные в безлимит, не имеют записи в журнале баланса; их список восстанавливается по аудиту окна, а не одной выборкой журнала.

## Решения владельца (2026-11-20, в чате)

1. Миграция `0042`: таблица `platform_settings` (allowlist ключей, `jsonb` по реестру Zod в `packages/shared`, `version` с 409 stale, `updated_by`, `updated_at`); отсутствие ключа = значение по умолчанию, равное текущему поведению; история — `audit_log` в той же транзакции, только изменённые ключи, no-op без аудита; root-only `GET/PATCH /api/platform/settings`; чтение через `getPlatformSettings()` с кэшем ~30 с, бот читает тот же источник (задержка принята и видна в UI); ошибка чтения — значения по умолчанию.

## 2. Безопасность по слоям

### 2.1 Инфраструктура и выкладка

**INF-01 (P1). Внутренний API открыт наружу.**
Доказательство: `Caddyfile` — всё, кроме пути webhook, проксируется на `web:3000`; `apps/web/server/api/internal/**` (бот: accept-offer, cancel-booking, chat-link, chat-member, games, my, reachable; invites preview; smoke cleanup); защита — заголовок `x-internal-secret` (`apps/web/server/utils/internal-auth.ts`). Лимита запросов на этих путях нет.
Риск: утечка одного секрета даёт действия от имени любого Telegram-пользователя (отмена записи, принятие места).
Действие: закрыть `/api/internal/*` в Caddy (ответ 404), оставить снаружи только `smoke/cleanup` с отдельным секретом; бот ходит на `web:3000` по сети compose. Разделить секреты: бот → web, web → бот, smoke.

**INF-02 (P1). Контейнеры от root и общий `.env`.**
Доказательство: `apps/web/Dockerfile`, `apps/bot/Dockerfile` — нет `USER`; `docker-compose.prod.yml` — `env_file` целиком для web и bot, нет `read_only`, `cap_drop`, `no-new-privileges`.
Риск: компрометация бота открывает `BETTER_AUTH_SECRET` и ключи S3; компрометация web — секреты webhook.
Действие: `USER node`; `cap_drop: [ALL]`, `security_opt: no-new-privileges`, `read_only` с tmpfs; отдельные env-файлы по сервисам с минимальным набором переменных.

**INF-03 (P2). Одна роль БД для приложения и миграций.**
Доказательство: `docker-compose.prod.yml` — роль `volley` (владелец схемы) у web, bot и мигратора.
Действие: роль `volley_app` без DDL для web и bot; владелец схемы — только у мигратора. Боту — доступ только к нужным таблицам либо только через внутренний API.

**INF-04 (P2). Образы и базовые теги не закреплены.**
Доказательство: `node:22-alpine`, `caddy:2-alpine`, `postgres:16-alpine` без digest; runtime-образ бота содержит полный `node_modules`.
Действие: закрепить digest, обновлять ботом зависимостей; убрать dev-зависимости из образа бота.

**INF-05 (P2). Заголовки безопасности.**
Доказательство: `Caddyfile` — HSTS без `includeSubDomains`; CSP с `script-src 'unsafe-inline'` и `style-src 'unsafe-inline'`; нет `Permissions-Policy` и явного `object-src 'none'` (`base-uri 'self'` и `form-action 'self'` уже заданы).
Действие: добавить недостающие директивы сразу; для `unsafe-inline` — отдельная задача на nonce/hash (проверить, что Nuxt SPA это допускает).

**INF-06 (P2). Резервные копии.**
Доказательство: `scripts/backup.sh` — шифрование age необязательно (при пустом `BACKUP_AGE_RECIPIENT` только предупреждение), дамп в открытом виде лежит в `/tmp`, хранение 21 день.
Действие: отказ без ключа шифрования; дамп в каталог с правами 0700 и удаление по `trap`; регулярный `restore-test.sh` по расписанию с оповещением.

**INF-07 (P2). Копии секретов на VPS.**
Доказательство: `.github/workflows/deploy.yml` — `.env.production` копируется в `/opt/volleytime/.deploy/incoming/<sha>/`.
Действие: проверить права и срок хранения этих копий; удалять после активации либо включить в ретенцию 9.8.18.

**INF-08 (P3).** `apps/bot/src/internal-server.ts` читает тело без ограничения размера; `healthz` и `/api/health` отдают SHA релиза, `/api/health` делает три запроса к БД без лимита. Действие: ограничить тело 64 КБ, добавить лимит на health, SHA отдавать только с внутренним секретом (smoke его использует — проверить).

### 2.2 CI/CD

**CI-01 (P1). Цепочка поставки выкладки.**
Доказательство: `.github/workflows/*.yml` — actions закреплены тегом, включая `appleboy/ssh-action@v1` и `scp-action@v1`, которым передаётся `VPS_SSH_KEY`; отпечаток хоста не закреплён; у большинства job нет блока `permissions`.
Действие: закрепить все actions по SHA; задать `fingerprint` хоста; `permissions: contents: read` по умолчанию; рассмотреть замену сторонних ssh-actions на `ssh`/`scp` из runner.

**CI-02 (P1). Нет автоматических проверок безопасности.**
Доказательство: в `.github/` только workflows; нет dependabot/renovate, `pnpm audit`, CodeQL, проверки секретов.
Действие: dependabot (npm, actions, docker), `pnpm audit --prod` как job с порогом high, включить secret scanning и push protection (репозиторий публичный), CodeQL для TypeScript.

**CI-03 (P2). Promote не работает на диапазонах с workflows.**
Доказательство: `docs/operations/status/current-state.md` — `PROMOTE_TOKEN` не задан, `prod` продвигался ручным `git push`.
Действие: завести токен с минимальными правами либо зафиксировать ручной путь как штатный и описать его проверки.

**CI-04 (P2).** Smoke использует настоящий токен бота на runner. Действие: проверить, что токен не попадает в логи и артефакты; рассмотреть отдельный smoke-путь без токена бота.

### 2.3 Аутентификация и сессии

**AUTH-01 (P1, проверить). Настройки better-auth по умолчанию.**
Доказательство: `packages/auth/src/config.ts` — нет явных `trustedOrigins`, атрибутов cookie, `rateLimit`. Защита собственных мутирующих `/api/**` от CSRF опирается только на SameSite cookie; проверки `Origin` нет.
Действие: задать `trustedOrigins` и атрибуты cookie явно; добавить серверную проверку `Origin`/`Sec-Fetch-Site` для не-GET запросов; покрыть тестом. Отдельно проверить вход Mini App в Telegram Web (iframe и SameSite).

**AUTH-02 (P2, проверить). Перебор email-кода.**
Доказательство: код из 6 цифр на 5 минут; лимитер — 20 запросов в минуту на клиента и путь (`apps/web/server/middleware/00.rate-limit.ts`). Ограничение по числу попыток на один код в конфигурации не задано явно.
Действие: явно задать число попыток на код (3–5) и лимит отправок на email; тест на блокировку.

**AUTH-03 (P2). Повтор initData.**
Доказательство: `packages/auth/src/telegram/validate.ts` — окно 1 час, защиты от повторного использования нет.
Действие: сократить окно входа (5–10 минут) либо хранить использованные `hash` до истечения окна. Для `link/telegram` — обязательно.

**AUTH-04 (P2). Привязка Telegram.**
Доказательство: `packages/auth/src/linking.ts` — проверки до транзакции (гонка упирается в unique и вернёт 500, а не 409); сообщение «сначала отвяжите его», но отвязки нет.
Действие: перенести проверки в транзакцию и перевести нарушение unique в 409; решить продуктово: отвязка или правка текста.

**AUTH-05 (P2, проверить). Управление сессиями.** Сессия 30 дней, одна cookie на все входы. Проверить, есть ли у пользователя «выйти со всех устройств», и отзываются ли сессии при блокировке платформой (нужно фазе 22).

**AUTH-06 (P3).** `TELEGRAM_LOGIN_WIDGET_ENABLED` выключен с v0.2.0. Либо включить с проверкой, либо убрать код (см. PROD-06).

### 2.4 Web API

**API-01 (P1). Лимит запросов.**
Доказательство: `apps/web/server/middleware/00.rate-limit.ts` покрывает только не-GET `/api/auth/*`, `/api/public/**`, `/e/<slug>` и публичный логотип. Без лимита: все авторизованные мутации, `/api/invites/[token]` и `redeem`, `/api/ownership-transfers/*`, `/api/internal/**`, `/api/health`. Лимитер в памяти процесса.
Действие: общий лимит на пользователя для мутаций; строгий лимит по IP на пути с токенами; лимит на экспорт. Память процесса допустима, пока экземпляр один, — зафиксировать это ограничение.

**API-02 (P2). Токены приглашений.**
Доказательство: `packages/core/src/invites/service.ts` — `nanoid(16)` (около 95 бит) против 24 символов у приглашений на событие и 32 байт у передачи владения.
Действие: энтропии достаточно; унифицировать длину (24) для новых ссылок и проверить, что у ссылок есть срок и лимит использований по умолчанию.

**API-03 (P2). Журнал действий.** Проверить покрытие аудита: смена ролей, исключение, финансовые операции, экспорт, передача владения, действия root. Для экспорта кассы и списков участников запись в журнал обязательна (выгрузка персональных и финансовых данных).

**API-04 (P3).** `TRUSTED_PROXY=1` берёт последний элемент `X-Forwarded-For`. Проверить, что Caddy перезаписывает заголовок и web недоступен в обход Caddy.

**BOT-02 (P2, проверить).** Внутренние ручки бота принимают `telegramUserId` от бота как истину. После INF-01 это допустимо; до него — главный риск.

**BOT-03 (P3).** Проверить поведение при блокировке бота пользователем и при 429 от Telegram: повтор, отметка недоставленного, отсутствие бесконечных повторов.

## 4. Интерфейсная реализация

**UI-01 (P2). Крупные компоненты.** 140 файлов `.vue`; `components/EventForm.vue` и `pages/m/orgs/[orgId]/events/[eventId]/index.vue` больше 40 КБ. Действие: разбить по секциям, вынести логику в composables с тестами.

**UI-02 (P2). Два интерфейса на одни сценарии.** Кабинет `/app/**` и Mini App `/m/**` повторяют экраны организатора. Действие: провести ревизию дублируемой логики (формы события, оплаты, касса) и вынести общее; иначе каждая правка делается дважды и расходится (см. требование «цифры совпадают» в v0.3.0).

**UI-03 (P2). Доступность.** `aria-` и `prefers-reduced-motion` встречаются в 110 файлах, но системной проверки нет. Действие: автоматическая проверка axe в CI для ключевых экранов; ручная проверка клавиатуры и контраста (ограничение по оранжевому цвету зафиксировано в 3.11.7).

**UI-04 (P2). Проверки на устройствах.** По `RELEASES.md` отчёта о проверках на устройствах для v0.2.0 нет. Действие: короткий обязательный чеклист (Android, iOS, Desktop, Telegram Web) с отметкой в QA-документе релиза. iOS в документах не упоминается вовсе.

**UI-05 (P3). Язык.** В 21.4.8 запланирована строка «Язык» в профиле. Действие: если перевода нет в планах — убрать строку из макета, а не реализовывать пустой переключатель.

**UI-06 (P3). Состояния ошибок.** В v0.1.6 находились ложные пустые состояния при ошибке загрузки (8.10.6). Действие: единый компонент «ошибка, повторить» и тест-шаблон для каждого списка.

**UI-07 (P3). Бот.** Кнопки макета («Буду», «Пропущу», «Мой абонемент», «Сборы», «Кто уже играет») перенесены в 21.4.9. Действие: проверить, какие из них нужны при работающем Mini App; дублирование удваивает поддержку.

## 6. Продукт

### 6.1 Что лишнее или преждевременное

**PROD-01 (P1). Ширина опережает проверку.** Метрика этапа MVP в PLATFORM_VISION: один организатор и 5+ игроков в неделю; критерий R0 «неделя реальных тренировок только через бота» остаётся открытым. При этом расписано 122 задачи фаз 19–26, включая Root Admin, SEO-страницы и две волны гипотез. В production две группы, списаний баланса на 2026-10-27 не было.
Действие: после v0.3.1 — пауза на эксплуатацию пилотной группы 2–4 недели с целями по метрикам; v0.4.0 и дальше планировать по её итогам.

**PROD-03 (P2). Root Admin как полный раздел (9 задач) до второго платящего организатора.** Для 2–5 организаторов бета-этапа достаточно операторских команд с журналом. Действие: сократить v0.4.0 до минимума (список организаций, выдача баланса, журнал), остальное — по потребности.

**PROD-04 (P2). Гипотезы (фазы 25–26, 11 задач) расписаны до метрик.** Решение по ним зависит от метрик 23.1.2, которые появляются только в v0.5.0. Действие: не детализировать карточки гипотез до появления данных; перенести 23.1.2 раньше (см. PROD-08).

**PROD-05 (P2). Баланс событий включён (`EVENT_BALANCE_ENFORCED`), а покупки нет.** Юридическая модель не выбрана, оплата — заявкой и ручным подтверждением root. Для пилота это трение без выручки. Действие: решение владельца — оставить как репетицию модели или выключить до выбора юрисдикции и способа оплаты.

**PROD-06 (P3). Неиспользуемые пути.** Login Widget за выключенным флагом; `legacy/python-prototype` в репозитории; роль `assistant`; `COLLECTIONS_ENABLED` выключен. Действие: для каждого — срок решения «включить или удалить»; прототип вынести в архивную ветку (в рамках 21.5).

**PROD-07 (P2). Документация как нагрузка.** `RELEASES.md` (481 строка) и `current-state.md` (267 строк) на три четверти состоят из исторических контрольных точек; сводка в `current-state.md` помечена 2026-09-21. 468 карточек задач. Действие: историю вынести в архивные файлы по релизам; `current-state.md` — одна страница; правило «новая запись заменяет старую».

### 6.2 Что упущено

**PROD-08 (P1). Продуктовые метрики.** Нет измерения активации и удержания: сколько организаторов создали событие, доля записей через Mini App, отмены, неявки, время до первой записи. Действие: минимальный набор событий и недельный отчёт владельцу — до v0.4.0, не в v0.5.0.

**PROD-09 (P1). Первый запуск организатора.** Сценарий «создал группу → пригласил игроков → первое событие» не описан как отдельный путь с подсказками; фаза 10 (onboarding, FAQ, обратная связь) отложена за v0.7.0. Действие: мастер первого запуска и чеклист в кабинете до приглашения внешних организаторов.

**PROD-10 (P1). Канал поддержки и обратной связи.** В интерфейсе не найдено «написать в поддержку» и сбора отзывов. Действие: кнопка обратной связи в Mini App и кабинете (сообщение владельцу платформы через бота).

**PROD-11 (P1). Юридический минимум** — см. PD-01; без него нельзя приглашать внешних организаторов и брать деньги за баланс.

**PROD-12 (P2). Перенос существующей группы.** Организатор приходит со списком игроков, долгами и абонементами в таблице. Импорта нет. Действие: импорт участников из CSV и ввод начальных остатков абонементов.

**PROD-13 (P2). Потеря доступа.** Что происходит, если владелец потерял Telegram-аккаунт и email не привязан: восстановления нет. Действие: настойчивое предложение привязать email владельцу; процедура восстановления через root с проверкой.

**PROD-14 (P2). Уход игрока и организатора.** Нет сценария «покинуть группу с долгом или остатком абонемента» как продуктового правила и нет закрытия группы с расчётами (открытый вопрос «purge финансовых записей»). Действие: правила в DOMAIN и экраны.

**PROD-15 (P2). Противоречия в PLATFORM_VISION (PROD-02).** Антицели: «полноценный web admin кабинет до проверки гипотезы», «сложный split-payments», «BI-платформа»; факт: кабинет со всеми разделами, split, отчёты и экспорт. Критический путь описывает фазы 7 и 10, заменённые референсом v3. Действие: обновить видение под решения 2026-10-12 или вернуть ограничения в план.

**PROD-16 (P3). Напоминания об оплате и долги.** Проверить, есть ли автоматическое напоминание должникам и сводка долгов организатору; для учёта денег это ключевая ценность.

**PROD-17 (P3). iOS и Telegram Web** не входят в матрицу проверки (см. UI-04).

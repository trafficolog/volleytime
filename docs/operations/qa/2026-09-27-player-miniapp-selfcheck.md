`scripts/qa/player-miniapp-real-screen-matrix.pwcode` использует email OTP
игрока и настоящие локальные API без подмены ответов. Пройдены 7 экранов
(`Мои группы`, Home, события, detail, записи, абонементы, профиль) × 320/390 px ×
light/dark = **28** снимков/геометрических проверок. Для каждого проверены
горизонтальное переполнение, доступность нижнего контента, dock и все видимые
`a`/`button` размером не меньше 44×44 px. Снимки также просмотрены визуально.

Начальный RED на Home 320 light: «Мои группы» 38×44, «Все события» 77×39;
отдельный аудит нашёл back в header 30×44 и ссылки карточек записей высотой
34 px. После записи дефекта в SDD минимальный класс `.vt-hit-44` применён к
этим четырём местам. Повторный прогон **28/28 GREEN**, без переполнения и
перекрытия dock. На реальном длинном месте Home 320: `scrollWidth=innerWidth=320`,
заголовок/место обрезаются с ellipsis, статус остаётся в границах;
тестовое название места восстановлено.

Существующий fixture regression `player-miniapp-fidelity.pwcode`:
**41/41**, 320/390 light/dark на основных экранах, локальные шрифты,
длинный текст, focus trap/Tab/Escape/возврат фокуса, CTA/dock и reduced motion.
`player-miniapp-group-race.pwcode` и `player-miniapp-network-retry.pwcode`
также прошли на локальной сборке. Эти скрипты используют контролируемые HTTP
ответы и не заменяют реальный API или Telegram.

## Реальные локальные потоки API/БД

Три QA-аккаунта вошли штатным email OTP; browser session и SQL подтвердили
соответствующих пользователей. Проверены:

1. Платная запись переводом `pending_payment`, отмена и возврат заполнения
   1/12 → 0/12; Home/список записей исключают отменённую активную запись,
   detail позволяет записаться заново.
2. Повторная запись абонементом `confirmed`: остаток 3 → 4 использованных
   занятия и обратно 4 → 3 после отмены; бесплатная запись `confirmed/free`.
3. Переполненное событие: `waitlisted/transfer` без платежа; второй игрок
   отменил место, сервер повысил первого до `pending_payment/transfer`, создал
   платёж и сохранил заполнение 1/1. Организатор подтвердил платёж в UI,
   запись стала `confirmed`, платёж `succeeded`.
4. Игрок купил абонемент переводом `pending`; организатор подтвердил его в UI.
   БД показала новый `active`, платёж `succeeded`, UI показал 8/8.
5. При выключенной функции абонементов активный остаток виден только для
   чтения, покупка не предлагается; при временном истечении вкладка скрыта,
   прямой маршрут показывает историю. Тестовый остаток восстановлен.
6. `pending`/`blocked` участник и `suspended` организация: шесть прямых
   маршрутов игрока показывают информационное состояние и выход «Мои группы»
   без CTA записи или ложного Retry. Исходные статусы восстановлены.
7. При изменении времени или переводе события в draft во время открытого
   detail сервер отклоняет устаревшие запись/отмену; клиент обновляет дату,
   убирает CTA или показывает ясный 404. Данные событий восстановлены.
   Неверная invite-ссылка показывает объяснение и выход.

Контрольный SQL: четыре published события; у игрока две active memberships,
три active subscriptions между двумя организациями. QA-записи: event 1
`cancelled/subscription`, event 2 `confirmed/free`, event 3
`confirmed/transfer`; другой игрок event 3 `cancelled/free`. Платежи QA:
`cancelled/transfer` 1500, `succeeded/transfer` 1500 и
`succeeded/transfer` 10000. `/api/health` ответил 200,
`db=ok`, `auth=ok`, `release=dev`. Это тестовые денежные состояния, не
подтверждение реального перечисления средств.

## Дополнение 2026-09-25: лист ожидания и настройка абонементов

На том же локальном стенде два тестовых аккаунта проверили заполненную бесплатную игру `1/1`. Второй аккаунт увидел «Встать в лист ожидания», выполнил действие и увидел «Вы в листе ожидания»; QA-БД сохранила `waitlisted`. Первый игрок затем отменил запись через нативный browser confirm с явным OK. Detail показал «Запись отменена» и `1/1` без ожидающих; QA-БД зафиксировала `cancelled` у первой записи и `confirmed` у бывшей ожидавшей. После нового входа второй аккаунт увидел «Вы записаны». Этот аккаунт является владельцем тестовой группы, поэтому его нижняя навигация — организаторская; подтверждены серверное повышение и общий экран события, но не Telegram-уведомление и не player-only навигация ожидавшего.

Для режима отключения абонементов временно установлены `subscriptions_enabled=false` только у локальной QA-группы. У игрока с ожидающим оплаты, но без **активного** остатка пункт «Абонементы» исчез из нижней навигации, прямой авторизованный URL остался доступен и показал сохранённую покупку без предложения новой. Затем единственный локальный QA-абонемент временно переведён из `pending` в `active` с остатком `4/4`: при всё ещё выключенной настройке пункт меню вернулся, Home и экран абонементов показали остаток и сообщение о режиме без новых покупок/записей. После проверки обе фикстуры восстановлены чтением БД: абонемент снова `pending` без дат активации/истечения, организация снова `subscriptions_enabled=true`. Это UI-проверка искусственного активного остатка, **не** подтверждение реальной оплаты организатором, списания или возврата занятия.

При снова включённой настройке и временно активном локальном остатке игрок отменил свою прежнюю `pending_payment`-запись и повторно записался на платное событие через пункт «Абонемент, осталось 4 из 4». Detail показал «Вы записаны», QA-БД — `booking=confirmed`, `method=subscription`, `subscription_id=1`, `used_sessions=1`. После отмены через UI detail показал «Запись отменена», а БД — `booking=cancelled`, `used_sessions=0`. Затем тестовый абонемент возвращён в `pending`, и игрок снова выбрал «Переводом» для платного события. Итоговая QA-БД: организация включена, абонемент `pending` с `0/4` использованных и пустыми датами активации/истечения, платная запись `pending_payment/transfer` без `subscription_id`. Бесплатная запись первого игрока осталась отменённой, а бывший ожидавший — подтверждённым; это намеренное состояние после теста повышения. Применение и возврат занятия подтверждены на искусственно активированном QA-остатке, но процесс подтверждения оплаты/активации организатором не проверялся.

## Дополнение 2026-09-25: доступ pending/suspended/blocked

При временном `pending` у QA-игрока Home показал «Заявка на рассмотрении», но прямой event detail до исправления показывал лишь «Не удалось открыть событие» и Retry. При временном `suspended` у QA-группы Home показал «Группа приостановлена», а прямой event detail — ту же общую ошибку. При временном `blocked` у QA-игрока Home и event detail тоже показывали общую ошибку. API не менялся: `GET event` закономерно отвергает неактивного участника, tenant middleware отвергает suspended/blocked до DTO. Дефекты записаны в SDD-карточку до кода.

RED-тесты проекций подтвердили неверный приоритет общей ошибки и отсутствие классификации `permission.blocked`, `permission.not_member`, `permission.no_longer_member`. После GREEN исправления новая собранная версия на прямом event URL показала для `pending` — «Заявка на рассмотрении», для `suspended` — «Группа приостановлена», для `blocked` — «Доступ в группу закрыт»; в каждом состоянии была ссылка «Мои группы», без записи и локальной action bar. Home и Profile для `blocked` также показали закрытый доступ вместо Retry. После возврата группы и участника в `active` detail снова показал действующую платную бронь. Обычный сбой загрузки группы остаётся ошибкой с повтором по unit-тесту; сетевой сбой в браузере специально не воспроизводился.

Полные gates после первой серии правок доступа: `pnpm format:check` — exit 0, `pnpm lint` — 0 ошибок/15 существующих предупреждений, `pnpm typecheck` — 6 успешных, `pnpm test` — 91 файл/507 тестов, `pnpm build` — 2 задачи. Один параллельный typecheck сначала получил временный `EPERM` на pnpm-lock; последовательный повторный запуск прошёл. Локальный QA-сервер остановлен, статусы группы и игрока подтверждены как `active`.

Следующий RED-тест зафиксировал классификацию tenant-ошибок для прямых списков. После GREEN общий информационный блок применён в `events`, `bookings`, `subscriptions` без изменения API. На новой локальной сборке все три маршрута при `pending` показали «Заявка на рассмотрении», при `suspended` — «Группа приостановлена», при `blocked` — «Доступ в группу закрыт»; в каждом случае есть «Мои группы», Retry отсутствует. `Profile` при `suspended` также показал информационный экран. После восстановления `active` все три маршрута снова загрузили действительные события, запись и абонемент. Итоговая QA-БД: организация `active`, абонементы включены, игрок `active`, абонемент `pending/used_sessions=0`; платная запись `pending_payment/transfer`, бесплатная запись первого игрока `cancelled`, повышенная из ожидания запись `confirmed`. Это локальные данные, не production.

Полные gates на последнем коде: `pnpm format:check` — exit 0, `pnpm lint` — 0 ошибок/15 прежних предупреждений после исправления нового import-order предупреждения, `pnpm typecheck` — 6 успешных, `pnpm test` — 91 файл/508 тестов, `pnpm build` — 2 задачи.

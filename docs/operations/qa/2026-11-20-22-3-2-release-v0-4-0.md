## Откат

- **Только приложение на `807f6857`** допустим без отката схемы (старый runtime не читает новые таблицу и колонку; решения владельца 2026-11-19 и runbook). Последствия, о которых предупредить владельца:
  - витрина снова продаёт пакеты из константы с прежними ценами; правки цен root и пакеты, созданные в Root Admin, недоступны; ожидающие заявки с `package_id` старый код подтверждает по снимку;
  - группы с безлимитом снова списывают баланс при публикации и останавливаются на нуле — перед откатом выполнить `SELECT id, name, event_balance_unlimited_until FROM organizations WHERE event_balance_unlimited_until > now();`, сообщить владельцу и при необходимости выдать баланс вручную после возврата вперёд;
  - настройки платформы игнорируются, действуют значения по умолчанию кода;
  - блокировка пользователей перестаёт действовать в вебе (бот по-прежнему читает `is_active`); Root Admin недоступен;
  - smoke и аккаунт №4: откат helper-ом (`scripts/deploy-image-bundle.sh rollback`, режим `rollback`) **внешний smoke не запускает** — он восстанавливает прежний runtime и проверяет только health; внешний smoke есть только в `deploy.yml` после активации. Поэтому после отката helper-ом аккаунт №4 остаётся активным (ни smoke, ни cleanup не выполняются). Старый код `807f6857` в вебе `is_active` не проверяет (флаг только пишет его cleanup), поэтому если позже выкладывается старый SHA через Deploy, его собственный старый smoke проходит, а старая уборка снова ставит №4 `is_active = false`; следующая выкладка нового кода включает аккаунт шагом prepare.
- Процедура: read-only аудит, затем `bash .deploy/incoming/<sha>/scripts/deploy-image-bundle.sh rollback <sha>` из staging кандидата ([runbook](../runbooks/deploy.md#exact-application-rollback)).
- **Откат схемы** — в обратном порядке, сначала `0042`, затем `0041`, каждый одной транзакцией (`pnpm db:rollback`):
  - `0042` отказывает, если в `platform_settings` есть любая строка или у любой организации `event_balance_unlimited_until IS NOT NULL` (даже истёкшее). Обход — решение владельца после `pg_dump -t platform_settings`.
  - `0041` отказывает, если каталог отличается от сида (любая правка, новый или архивированный пакет) или есть заявки с `package_id`, созданные после сида. Обход — решение владельца после `pg_dump -t event_balance_packages -t event_balance_purchase_requests`.
  - **Откат схемы закрывается быстро и без действий root.** `0041` закрывается первой обычной заявкой организатора на покупку после выпуска: новый код пишет `package_id`, заявка создана после сида — guard срабатывает. `0042` закрывается любым сохранением настройки root или установкой безлимита — в том числе плановым QA на устройствах (сохранение контакта поддержки, безлимит тестовой организации). Отмена безлимита (`packages/core/src/platform/event-balance-unlimited.ts`) ставит колонку в `NULL`, поэтому по колонке guard снова пропускает, но строка в `platform_settings` остаётся и guard по ней не снимается.
  - Вывод: на практике после выпуска — только roll-forward по схеме; реальный запасной путь — откат только приложения.
